# AI 招标文件合规审查系统 — 验证

本文档与 [设计.md](./设计.md) 中的各模块一一对应，每个模块覆盖 **验证目标 → 验证用例 → 期望产出**，
与设计、实现形成 **设计 → 实现 → 验证** 的闭环。

验证总原则：

- **确定性验证优先**：规则引擎（无 LLM）模块，相同输入必须产生相同输出 — 精确回归测试可行。
- **分层验证**：单元验证（函数级）→ 模块验证（Step 级）→ 集成验证（全链路）。
- **Golden Data 策略**：用真实标书的已知正确输出作为回归基准。


**用例 V2.1 — 文本清洗**

```
前置条件: 准备含中文绝对定位字符的 PDF（已知 layout raw_text）

验证步骤:
  1. 对每页的 raw_text 调用 clean_layout_text()
  2. 检查输出文本中不存在 "字  字" 模式（中文字符间不应有
     连续空格，即 CJK 字符之间的空格已被合并）

测试输入构造:
  输入: "投  标  人  须  在  东  莞  地  区  设  有  常  驻  服  务  机  构"
  期望: "投标人须在东莞地区设有常驻服务机构"

  输入: "符合  以下  条件"（英文词间保留 2 空格）
  期望: "符合  以下  条件"

  输入: "第一章  总  则\n第二条  合同  标的"
  期望: "第一章  总则\n第二条  合同标的"

通过标准:
  - CJK_SPACE_RE 规则：中文字符间不再出现空格（"字字" OK，"字 字" NG）
  - MULTI_SPACE_RE 规则：所有连续空格被压缩为 2 空格
  - 迭代最多 5 轮收敛（不无限循环）
```

**用例 V2.2 — 单词 ID 和 BBox**

```
前置条件: 对已知结构的 PDF 执行 extract_pdf_to_raw_json()

验证步骤:
  1. 遍历所有 pages[].words[]
  2. 对每个 word:
     a. 验证 id 格式匹配 Regex: ^w_\d+_\d+$
     b. 验证 id 的前缀页号与 page_index 一致
     c. 验证 bbox 约束:
        - x0 ≤ x1（宽度非负）
        - top ≤ bottom（高度非负）
        - x0 ≥ 0, x1 ≤ page.width（水平在页面内）
        - top ≥ 0, bottom ≤ page.height（垂直在页面内）
     d. 验证 text 非空（空字符串的 word 应被过滤）
  3. 验证同一页内 word id 的序号从 0 开始连续递增（无跳号）

通过标准:
  - 100% word 满足 ID 格式约束
  - 100% word 满足 BBox 几何约束
  - 每页 word 序号连续
```

**用例 V3.1 — 七种标题模式匹配**

```

测试数据（每行对应一个模式）:
  第一章 磋商邀请                          → level=1, pattern=chapter
  第二节 项目概况                          → level=2, pattern=section
  一、供应商资格要求                       → level=2, pattern=cjk_numbered
  二.项目预算                             → level=2, pattern=cjk_numbered
  （一）基本资格条件                       → level=3, pattern=paren_cjk
  (二) 特定资格要求                       → level=3, pattern=paren_cjk
  1. 具有独立承担民事责任的能力              → level=4, pattern=digit_dot
  2、具有良好的商业信誉                     → level=4, pattern=digit_dot
  3)健全的财务会计制度                      → level=4, pattern=digit_dot
  （1）营业执照副本                        → level=5, pattern=paren_digit
  (2) 法定代表人证明                       → level=5, pattern=paren_digit

  2. 验证匹配到的 level 与设计文档的映射表一致
  3. 边界 case 验证: 空行不匹配、仅有编号而无后续字符的不匹配
```

#### 用例 V4.3 — 规则 3：相邻短叶子合并（含页面间隙控制）

```
前置条件: 构造同一父节点下有多个短叶子的树

测试数据:
  场景 A（基本合并）: 父节点下一组短叶子

    → 合并为 1 个 chunk, chunk_type == Merged { rule: "adjacent_merge", child_count: 4 }

  场景 B（混合长度）: 3 个叶子 [30字, 120字, 25字]
    → 第1个入缓冲 → 第2个 ≥ 120，先 flush 缓冲（第1条单出），
      第2条独立 Leaf，第3条入新缓冲
    → 3 个 chunk: Leaf, Leaf, Leaf

  场景 C（合并超限提前 flush）: 多个叶子合并后 > 1500 字
    → merge_len > split_max_len 时提前 flush，产生多个 chunk
    → 每个 chunk ≤ split_max_len

  场景 D（全部长叶子）: 全部叶子 ≥ 120 字
    → 各自成 Leaf，不触发合并

  场景 E（页面间隙过大）: 叶子间 page gap > MAX_MERGE_PAGE_GAP (2)
    → 提前 flush 当前缓冲区，远距离叶子进入新合并组
    → 验证 page span 不膨胀

验证步骤:
  1. 对每个场景调用 chunk_sections()
  2. 检查 chunk_type 和 child_count
  3. 检查每个 chunk ≤ split_max_len
  4. 场景 E 中验证 page_end - page_start 不异常膨胀

通过标准:
  - merge_min_len=120: <120 进入合并候选，≥120 单独 Leaf
  - 合并中总长触及 split_max_len 时提前 flush
  - child_count 准确反映实际合并的叶子数
  - 页面间隙 > 2 时正确拆分合并组
```

```
通过标准:
  - 切分点在段落边界或安全断点
  - overlap 区域语义合理（非中间截断）
  - Split.part 和 Split.total 编号正确

```

#### 用例 V5.1 — embed_text 格式

```
前置条件: 取已有 Chunk 列表（如清华标书 161 chunks）

验证步骤:
  1. 对每个 chunk 调用 embed_text(ctx_depth=2, max_path_len=40):
     期望格式: 【L(N-1) > L(N)】\n{chunk.text}
  2. 验证前缀非空（除非 section_path 为空）
  3. 验证前缀以【开头、】结尾
  4. 验证前缀中的标题链与 section_path 后 ctx_depth 级一致
  5. 验证 max_path_len=40 时，单级标题 > 40 字符的部分被截断为"…"

边界 case:
  - section_path 为空 → embed_text = chunk.text（无前缀壳）
  - ctx_depth > section_path.len() → 取全部, 不 panic
  - chunk.text 为空 → 仍产生前缀（chunk 可能为纯标题占位）

通过标准:
  - 100% chunk 的 embed_text 前缀格式正确
  - 前缀内容与 section_path 一致
  - 无【】空壳
```

#### 用例 V5.3 — L2 归一化 ⭐

```
前置条件: 已有 BGE-M3 输出向量（如 vectors_1024d_f32le.bin）

验证步骤:
  1. 对每个向量 v，计算 L2 范数 = sqrt(Σ(v[i]²))
  2. 统计所有范数: min, max, mean, std

期望结果（基于清华标书实测）:
  | 指标 | 期望值 | 说明 |
  |------|--------|------|
  | L2 norm min | 0.9999 ~ 1.0001 | 归一化后应为单位向量 |
  | L2 norm max | 0.9999 ~ 1.0001 | 同上 |
  | L2 norm mean | 1.0000 | 均值严格为 1 |
  | L2 norm std | < 1e-5 | 几乎无波动 |

通过标准:
  - 所有向量范数 ∈ [0.9999, 1.0001]
  - 无零向量（范数 = 0）→ 如有则 embedding 服务 bug
```

#### 用例 V5.4 — 语义区分度 ⭐（核心质量指标）

```
原理: 语义相似的 chunk（同章节、同主题）应有更高的余弦相似度；
      语义无关的 chunk（跨章节、不同主题）应有较低的余弦相似度。
      如果所有 chunk 相似度都接近 1.0 → 嵌入坍塌（collapse）；
      如果所有 chunk 相似度都接近 0.0 → 嵌入无意义（随机噪声）。

前置条件: 已有 N×1024d 归一化向量矩阵 + chunk 元数据（section_path）

验证步骤:
  1. 计算全量 pairwise 余弦相似度矩阵（N×N）
  2. 分组统计:

  组 A — 同一父章节内的 chunk pairs:
    - 条件: section_path 的前 N-1 级相同（如都在"第三章 > 二、详细评分细则"下）
    - 期望: mean_cos 较高（> 0.75）

  组 B — 跨一级章节的 chunk pairs:
    - 条件: section_path 的第一级不同（如"第一章" vs "第四章"）
    - 期望: mean_cos 较低（< 组A 均值）

  组 C — 随机采样 500 对:
    - 期望: 均值在 0.50 ~ 0.85 之间（标书文本天然有共同法律语言）

  3. 统计检验:
     - 组 A 均值 > 组 B 均值（差异 ≥ 0.05）
     - 组 A 和组 B 的相似度分布有明显的分离度

基于清华标书 161 chunks 的参考值:
  | 分组 | 预期 mean_cos | 说明 |
  |------|--------------|------|
  | 同章节 (组A) | 0.75 ~ 0.90 | 同一主题条款高度相关 |
  | 跨章节 (组B) | 0.50 ~ 0.70 | 不同章节共享法律语言基础 |
  | 全量 | 0.60 ~ 0.75 | 标书整体具有一定语义一致性 |
  | 随机对 | 0.55 ~ 0.75 | 同上 |

通过标准:
  - 组 A mean_cos > 组 B mean_cos（差值 ≥ 0.05）
  - 无 pair cos = 1.0000（排除重复向量）
  - 无 pair cos < 0.3（排除异常无关向量——标书文档天然有共同语言）
  - 全量 mean_cos ∈ [0.55, 0.85]
```

#### 用例 V5.5 — 维度坍塌检测 ⭐

```
验证步骤:
  1. 向量值分布检查:
     - 读取全部 N×D 个浮点值
     - 统计 min, max, mean, std
     - 期望: mean ≈ 0, std > 0.05（有区分度）

  2. 零向量检测:
     - 逐行检查范数，范数 = 0 的向量 → 嵌入失败，报错

  3. 全等向量检测:
     - 对每对向量计算 cos
     - cos = 1.0000 且文本不同 → 嵌入坍塌，严重问题

  4. 维度方差:
     - 对每个维度 d，计算该维在所有 N 个向量上的方差
     - 统计各维方差的分布
     - 期望: 所有维度方差 > 0（每个维度都参与了编码）
     - 方差为 0 的维度 → "死维度"（dead neuron），表示模型未充分利用

  5. 向量值饱和度:
     - 统计落在 [-0.5, 0.5] 之外的值占比
     - 期望: > 99% 的值在此区间（归一化 1024d 向量的自然属性）

基于清华标书 161 chunks 的参考值:
  | 指标 | 实测值 | 判断 |
  |------|--------|------|
  | value min | -0.205 | ✅ 无饱和 |
  | value max | +0.263 | ✅ 无饱和 |
  | value mean | -0.001 | ✅ 中心化良好 |
  | L2 norm 范围 | 1.0000 ~ 1.0000 | ✅ 完美归一化 |

通过标准:
  - 零向量数 = 0
  - 全等向量对数 = 0
  - 值域 ∈ [-1.0, +1.0]，无 NaN/Inf
  - mean 绝对值 < 0.01（近似零中心）
```

#### 用例 V5.6 — 语义搜索端到端验证 ⭐

```
前置条件: 已构建 DocumentVectorIndex（161 条向量 + chunk_meta）

验证步骤:
  1. 准备 5 条典型 Agent 查询语句（模拟审查场景）:
     查询 1: "供应商需要具备哪些资格条件？"
     查询 2: "本项目不接受联合体投标的要求"
     查询 3: "投标文件的密封和递交要求"
     查询 4: "付款方式和结算条件是什么"
     查询 5: "技术服务的验收标准和流程"

  2. 对每条查询:
     a. 用 BGE-M3 编码查询文本 → 1024d query_embedding
     b. 调用 index.search(query_embedding, top_k=5)
     c. 输出 Top-5 结果的:
        - chunk_id, title, score, snippet (前 200 字), page

  3. 人工评判每条查询的 Top-3:
     □ Hit-1: 第 1 名是否真正与查询语义相关？
     □ Hit-3: 前 3 名中至少 2 条相关？
     □ Miss: 是否有明显应命中但未出现在 Top-5 的 chunk？

  4. 定量指标:

     - Recall@5: Top-5 命中了多少个人工标注的相关 chunk（需预先标注）

通过标准:
  - 5 条查询的 Precision@3 均值 ≥ 0.6（即 Top-3 中平均 ≥ 2 条相关）
  - 5 条查询的 MRR ≥ 0.5（相关结果排名靠前）
  - 无明显 Miss（人工确认应命中但 Top-5 均未出现的情况 = 0）
```

### 5.6 嵌入管线位置

```
output/chunks/{文档名}_chunks.json          ← §4 Chunk 切分输出
        │
        ▼
embedding_service::embed_chunks(&chunks, &config)
        │
        ├─ embed_text(ctx_depth=2, max_path_len=40)   ← 每个 chunk 带层级前缀
        ├─ Bgem3Embedding::try_new(options)            ← 加载 ONNX 模型
        ├─ model.embed(texts, batch_size)              ← 批量编码 → 1024d
        ├─ L2 Normalize (in DocumentVectorIndex::new)
        │
        ▼
output/embeddings/{文档名}_embedding_index/
        ├─ chunk_meta.json                ← document_id + ChunkMeta[]
        └─ vectors_1024d_f32le.bin        ← N×1024 f32 LE
                │
                ▼
        Agent search_document 工具         ← 暴力余弦相似度 Top-K
```

嵌入管线的上游是 Chunk 切分（§4），下游是 Agent 的 `search_document` 工具。
如果嵌入质量不达标（如语义区分度低），应优先排查：
1. Chunk 切分是否有大量碎片 → 调整 `merge_min_len`
2. embed_text 的 ctx_depth 是否合适 → 调整 `embed_ctx_depth`
3. BGE-M3 模型文件是否完整 → 检查 models/ 目录和 ONNX 文件完整性

### 9.1 Episodic Memory（短期记忆）

### 9.2 Session Memory（中期记忆 — SessionGraph）

```
验证目标: SessionGraph 在完整管线中的生命周期

  用例 9.2-A — 生命周期:
```


### 13.3 并发边界

```
    - 不会出现 "poisoned lock" panic
```

```powershell
# 脚本: scripts/run_agent_tests.ps1 中也可配合 PDF 测试，此处保留原有 E2E 验证
param(
    [string]$PdfPath = "tests/file/智慧教室环境改造工程.pdf",
    [int]$MaxClauses = 5
)

Write-Host "=== Agent 端到端验证 ===" -ForegroundColor Cyan
Write-Host "PDF: $PdfPath" -ForegroundColor Gray
Write-Host "Max Clauses: $MaxClauses" -ForegroundColor Gray

    "Coordinator 启动" = $output | Select-String "Coordinator: Multi-Agent 审查管线启动"
    "Chunk 加载"       = $output | Select-String "已加载.*Chunk"
    "LLM 就绪"         = $output | Select-String "LLM 客户端就绪"

        Write-Host "  [FAIL] $($check.Key)" -ForegroundColor Red
        $allPassed = $false
    }

        Write-Host "  [WARN] findings 为空（可能所有条款都合规）" -ForegroundColor Yellow
    }
} else {
    Write-Host "  [FAIL] findings.json 未生成" -ForegroundColor Red
    $allPassed = $false
}

if ($allPassed) {
    Write-Host "`n=== 端到端验证通过 ===" -ForegroundColor Green
} else {
    Write-Host "`n=== 端到端验证存在失败项 ===" -ForegroundColor Red
    Write-Host "完整输出请查看上方日志。" -ForegroundColor Gray
}
```
