# AI 招标文件合规审查系统 — 实现

## 3. 文档解析与结构化管线

将原始投标文件（`.docx`）转化为下游 Agent 可直接消费的结构化数据。整条管线分三步，全部采用**确定性规则引擎**，无 LLM 参与。

```
.docx / .doc 文件
    │
    ▼
┌─ Step 1: DOCX → PDF ──────────────────────────────────────────────┐
│  src/services/docx_convert_service.rs                              │
│  LibreOffice headless 模式转换                                      │
└───────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ Step 2: PDF → RawDocument ───────────────────────────────────────┐
│  src/services/pdf_extract_service.rs (Rust 主引擎)                  │
│  scripts/pdf_extract.py (Python 兜底引擎)                           │
│  src/domain/raw_document.rs (数据模型)                               │
└───────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ Step 3: RawDocument → Section 树 ────────────────────────────────┐
│  src/services/sectionize_service.rs                                 │
│  7 种中文标题模式 → 嵌套章节树                                       │
└───────────────────────────────────────────────────────────────────┘
    │
    ▼
  下游消费: Chunk 切分（§4）→ Embedding → Agent 审查
```

### 3.1 Step 1: DOCX → PDF 转换

实现文件：[`src/services/docx_convert_service.rs`](../src/services/docx_convert_service.rs)

#### 技术选型

选择 **LibreOffice headless** 而非 python-docx 直读，原因：下游管线依赖 PDF 页面坐标体系（BBox），`python-docx` 能取文本但无法还原排版位置，而高亮回溯需求要求每个词都有精确的页面坐标。

| 方案 | 结论 |
|------|------|
| LibreOffice headless | ✅ 采用 — 免费、保真度高、命令行可调用 |
| Microsoft Word COM | ❌ 仅 Windows、需 Office 授权 |
| python-docx 直读 | ❌ 丢失页面坐标，与 PDF 提取管线不兼容 |
| 在线转换 API | ❌ 隐私风险、网络依赖 |

#### 核心函数


#### 错误处理

| 错误场景 | 检测方式 | 错误信息 |
|----------|---------|---------|
| LibreOffice 未安装 | `find_soffice()` 返回 `Err` | "请安装 LibreOffice 或设置 LIBREOFFICE_PATH 环境变量" |

| 输出 PDF 未生成 | 文件系统检查 | "LibreOffice 未生成 PDF 文件" |

#### 数据模型

**ID 命名规范**：

| 层级 | 前缀 | 格式 | 示例 |
|------|------|------|------|
| Word | `w_` | `w_{页码}_{序号}` | `w_3_15` |
| Block | `b_` | `b_{页码}_{序号}` | `b_5_2` |
| Table | `t_` | `t_{页码}_{序号}` | `t_2_0` |

**BBox 坐标系**：原点在页面左上角，X 向右，Y 向下（与 PDF 坐标系一致）。

```rust
pub struct BBox {
    pub x0: f64,      // 左边界
    pub top: f64,     // 上边界（距页顶）
    pub x1: f64,      // 右边界
    pub bottom: f64,  // 下边界
}
```

#### 文本清洗：两大正则规则

中文标书 PDF 常用绝对定位渲染每个字符，`layout=True` 产生大量填充空格。清洗管线使用与 Python 引擎完全相同的逻辑：

```
原始: "投  标  人  须  在  东  莞  地  区  设  有  常  驻  服  务  机  构"
清洗后: "投标人须在东莞地区设有常驻服务机构"
```

```rust
// 规则1: 合并被空格拆散的中文词组（[一-鿿])\s+([一-鿿]) → $1$2）
// 迭代最多 5 轮
static CJK_SPACE_RE: LazyLock<Regex> = LazyLock::new(|| {
    Regex::new(r"([一-鿿])\s+([一-鿿])").expect("CJK regex")
});

// 规则2: 压缩连续空格（2+ 空格 → 2 空格，保留词间分隔）
static MULTI_SPACE_RE: LazyLock<Regex> = LazyLock::new(|| {
    Regex::new(r" {2,}").expect("multi-space regex")
});
```

#### 文本重建：从单词坐标建文本

当 `clean_layout_text` 后文本长度不足原始的 20% 时触发。Rust 和 Python 引擎实现相同算法：

```
reconstruct_text_from_words():
  1. 取所有 word 高度的中位数 → line_height
  2. 按 (top, x0) 排序
  3. 按 Y 坐标分组为行: word.top - 当前行 top < 1.2×line_height → 同一行
  4. 行内按 X 排序，按列间距分"列段":
     列间距 < 8× 平均字符宽度 → 同一列段
     列间距 ≥ 8× 平均字符宽度 → 新列段（表格/多列布局）
  5. 列段间用双空格连接，行间用换行连接
```

#### 段落块（Block）聚合算法

从离散单词 → 语义段落块的聚合算法，Rust 和 Python 引擎完全一致：

```
compute_blocks(words, page_index):
  Step 1 — 按 Y 坐标分组为"文本行": 垂直间距 < 1.2×line_height → 同一行
  Step 2 — 按行间距合并为"段落块": 行间距 > 1.8×line_height → 段落边界
  Step 3 — 构建 Block:
    bbox = 块内所有 word 的并集矩形
    id = "b_{page_index}_{block_index}"
    type = heading (单行 ≤ 10 词) | paragraph
    text = 各行文本拼接
  const HEADING_GAP_RATIO: f64 = 1.8;
```

```
示意:
┌────────────────────────────────────────┐
│  第三章 评审方法和标准           ← b_3_0 │  (单行 ≤ 10词 → heading)
│  3.1 评审方法采用综合评分法...   ← b_3_1 │  (多行 → paragraph)
│  总分为100分，其中技术部分占60分...     │
│  3.2 评审程序                   ← b_3_2 │  (行间距 > 1.8× → 新段落)
└────────────────────────────────────────┘
```

### 3.3 Step 3: RawDocument → Section 树构建

实现文件：[`src/services/sectionize_service.rs`](../src/services/sectionize_service.rs)

#### 技术选型：为什么用正则而不用 LLM

| 维度 | 正则规则引擎 (当前方案) | LLM 方案 |
|------|----------------------|----------|
| 标题模式 | 中文标书标题高度规整，正则可 100% 覆盖 | 适合非结构化，标书本就结构化 |
| 层级判定 | 模式→层级映射确定性的 | 需理解上下文，可能不一致 |
| 速度 | 615 section < 10ms | 数十秒 |
| 成本 | 零 | 数千 tokens/份 |

#### 七种标题模式 → 五级层级

按优先级排列，靠前的先匹配（一行只匹配一个模式）：

```rust
static HEADING_PATTERNS: LazyLock<Vec<HeadingPattern>> = LazyLock::new(|| {
    vec![
        // Level 1: 第X章
        HeadingPattern { pattern_type: "chapter", level: 1,
            regex: Regex::new(r"^第[一二三四五六七八九十百千]+章") },
        // Level 2: 第X节
        HeadingPattern { pattern_type: "section", level: 2,
            regex: Regex::new(r"^第[一二三四五六七八九十百千]+节") },
        // Level 2: 一、二、三、...
        HeadingPattern { pattern_type: "cjk_numbered", level: 2,
            regex: Regex::new(r"^[一二三四五六七八九十百千]+[、.．]\s*\S") },
        // Level 3: （一）（二）...
        HeadingPattern { pattern_type: "paren_cjk", level: 3,
            regex: Regex::new(r"^[（(][一二三四五六七八九十百千]+[）)]\s*\S") },
        // Level 4: 1. 2、3) ...
        HeadingPattern { pattern_type: "digit_dot", level: 4,
            regex: Regex::new(r"^\d+[.、)）]\s*\S") },
        // Level 5: （1）（2）(1) ...
        HeadingPattern { pattern_type: "paren_digit", level: 5,
            regex: Regex::new(r"^[（(]\d+[）)]\s*\S") },
        // Level 4: 第X条 (合同条款)
        HeadingPattern { pattern_type: "article", level: 4,
            regex: Regex::new(r"^第[一二三四五六七八九十百千]+条") },
    ]
});
```

**优先级设计逻辑**：`第X章` 必须排第一——`一、` 和 `1.` 既可作章标题也可作节标题，`chapter` 和 `section` 是最明确的层级信号，必须优先消费。

#### 三重过滤规则

**过滤 1 — 纯数字行（页码）**

```rust
fn is_page_number(line: &str) -> bool {
    let trimmed = line.trim();
    if trimmed.len() > 3 { return false; }
    trimmed.chars().all(|c| c.is_ascii_digit() || c == ' ')
}
// "1" → true, "92" → true, "第一章" → false
```

**过滤 2 — 数字序号匹配行过长**

```rust
// level >= 4（digit_dot）且标题 > 80 字符 → 大概率是条款正文中的编号，跳过
if pattern.level >= 4 && title.chars().count() > 80 {
    continue;
}
```

**过滤 3 — 同一行匹配多个模式** → 取层级最高的（level 数值最小）。

#### 树构建算法：两阶段栈式组装

```
Phase 1 — 扫描构建扁平列表 + 记录父子关系
  遍历 HeadingCandidate[]:
    维护"祖先栈" stack
    对于当前候选:
      ① 弹出栈中所有 level >= 当前 level 的节点
      ② 父节点 = 栈顶（最近的 level 更低的节点）
      ③ 当前节点入栈 → 记录 parent_of[i]

Phase 2 — 收集子节点索引
  children_of[i] = {所有 parent_of[j] == i 的 j}

Phase 3 — 递归组装树
  从根节点 (parent_of[i] == None) 出发:
    递归 take_section_from_flat():
      取出 sections[idx]，遍历 children_of[idx]，组装 Section.children
```

**栈变化示意**：

```
候选: [第一章(L1), 一、概述(L2), （一）范围(L3), 二、要求(L2)]

第一章:    push → [第一章]                    parent=无
一、概述:  push → [第一章, 一、概述]           parent=第一章
（一）:    push → [第一章, 一、概述, （一）]    parent=一、概述
二、要求:  L2 → pop(L3), pop(L2)
           push → [第一章, 二、要求]           parent=第一章

树: 第一章
      ├── 一、概述
      │     └── （一）范围
      └── 二、要求
```

完整实现参见 [`build_section_tree()`](../src/services/sectionize_service.rs)。

#### 输出数据结构

```rust
pub struct Section {
    pub level: u8,                // 1=章, 2=节, 3=小节, 4=条目, 5=子条目

    pub pattern: String,          // 匹配的模式类型
    pub page_start: usize,        // 标题所在起始页码 (0-based)
    pub page_end: usize,          // section 子树涵盖的最大页码 (0-based)
    pub block_ids: Vec<String>,   // 本节包含的所有 block ID（回溯高亮）
    pub body_page_start: usize,   // body_text 实际来源起始页 (0-based)，#[serde(default)]
    pub body_page_end: usize,     // body_text 实际来源结束页 (0-based)，#[serde(default)]
    pub body_text: String,        // 正文（标题之下、子标题之上），不含标题行本身
    pub children: Vec<Section>,   // 子章节（递归嵌套）
}

pub struct SectionizeOutput {
    pub document_id: String,
    pub source_path: String,
    pub sections: Vec<Section>,
    pub stats: SectionizeStats,   // total_sections, level_counts, orphan_blocks
}
```

> **`page_start`/`page_end` vs `body_page_start`/`body_page_end`**：
> - `page_start`/`page_end` 描述 Section 子树的全页面范围（标题所在页 到 子树最末页），用于排序和层级关系
> - `body_page_start`/`body_page_end` 描述 `body_text` 的实际来源页码范围
> - 对于叶子节点，两者通常接近；对于容器节点（有子节点），`page_end` 可能比 `body_page_end` 大很多（数十页差）
> - **Chunk 切分统一使用 `body_page_start`/`body_page_end`** 作为 chunk 的 page 范围，避免容器引言和合并 chunk 的 page span 膨胀

**输出位置**：`output/sections/{文档名}_sections.json`

#### 孤儿 Block 处理

不归属于任何 Section 的 block（如封面、目录页）：
- 保留在 RawDocument 中供全文搜索使用
- 在 Agent 的 `search_document` 工具中可被命中
- `stats.orphan_blocks` 作为数据质量指标——异常高（> 30%）说明标号体系未被覆盖

## 4. 条款级 Chunk 切分策略

从 Section 树到条款级 Chunk，核心原则：**一个 chunk = 一个可以独立理解、独立评估的完整语义单元**。不是简单地把每个叶子节点当成一个 chunk。

### 4.3 主入口

```rust
// src/services/chunking_service.rs

/// 从 Section 树切分为 Chunk 列表。
///
/// 流程：
/// 1. 逐个 Section 递归遍历，应用规则 1-4 切分
/// 2. 按 page_start 排序，分配 chunk_id（ch_000, ch_001, ...）
/// 3. 后处理 A：merge_tiny_chunks() 合并碎片 chunk
/// 4. 后处理 B：dedup_chunks() 精确去重
/// 5. 每次修改列表后重新分配 chunk_id
pub fn chunk_sections(sections: &[Section], config: &ChunkingConfig) -> Vec<Chunk> {
    let mut chunks = Vec::new();
    for section in sections {
        traverse_and_chunk(section, &Vec::new(), config, &mut chunks);
    }

    // 按页面顺序排序并分配 chunk_id
    chunks.sort_by_key(|c| c.page_start);
    for (i, chunk) in chunks.iter_mut().enumerate() {
        chunk.chunk_id = format!("ch_{:03}", i);
    }

    // 后处理：合并碎片 chunk
    if config.min_chunk_size > 0 {
        chunks = merge_tiny_chunks(chunks, config);
        for (i, chunk) in chunks.iter_mut().enumerate() {
            chunk.chunk_id = format!("ch_{:03}", i);
        }
    }

    // 后处理：精确去重
    chunks = dedup_chunks(chunks);
    for (i, chunk) in chunks.iter_mut().enumerate() {
        chunk.chunk_id = format!("ch_{:03}", i);
    }

    chunks
}
```

### 4.4 规则 1 — 自包含叶子节点直接成 chunk

有 `body_text` 且无子节点的 section 是完整语义单元，直接成为 Leaf 型 chunk：

```rust
fn try_chunk_leaf(
    section: &Section, parent_path: &Vec<String>,
    config: &ChunkingConfig, chunks: &mut Vec<Chunk>,
) -> bool {
    // 条件: body_text 非空 && children 为空
    if section.body_text.is_empty() || !section.children.is_empty() {
        return false;
    }
    let mut path = parent_path.clone();
    path.push(section.title.clone());
    let text = format!("{}\n{}", section.title, section.body_text);

    // 过长 → 规则4硬切
    if text.chars().count() > config.split_max_len {
        split_long_chunk(path, text, section, config, chunks);
        return true;
    }

    chunks.push(Chunk {
        chunk_id: String::new(),
        chunk_type: ChunkType::Leaf,
        section_path: path, text,
        // 使用 body 实际页范围：精确反映正文所在页码
        page_start: section.body_page_start,
        page_end: section.body_page_end,
        source_block_ids: section.block_ids.clone(),
    });
    true
}
```

```
示例:

→ chunk_042:

    section_path: ["第一章 磋商邀请", "三.获取磋商文件"]
    text: "三.获取磋商文件\n时间：详见磋商公告..."
```

### 4.6 规则 2 — 纯容器节点向下传递路径，子节点分区处理

`body_text` 为空的容器不单独成 chunk，递归处理子节点时带上容器标题作为上下文。

遍历时分离两类子节点：
- **叶子**：无子节点 + `body_text` 非空 → 走规则 3 合并逻辑
- **容器**：有子节点（不论 body_text）→ 递归传递路径

纯标题占位节点（`body_text` 为空 + 无子节点）：若标题非空则生成最小 Leaf chunk，保留模板结构信息。后续被 `merge_tiny_chunks` 合并到相邻同路径 chunk，不会产生碎片污染。

```

    L5: 2）有依法缴纳税收...                 ← 叶子
```

Agent 审查资格条件时，一个 chunk 包含法条全部条件，无需跨 chunk 拼凑。

### 4.7 规则 3 — 相邻独立叶子合并（含页面间隙控制）

同一父节点下，多个独立叶子如果各自太短（< `merge_min_len` = 120 字），合并为一个语义完整的 chunk。

**页面间隙控制**：叶子与缓冲区页面间隙 > `MAX_MERGE_PAGE_GAP`（2 页）→ 提前 flush，避免远距离格式模板页被合并进同一 chunk 导致 page span 膨胀。

```rust
fn merge_adjacent_leaves(
    leaves: &[&Section], parent_path: &Vec<String>,
    config: &ChunkingConfig, chunks: &mut Vec<Chunk>,
) {
    let mut merge_buffer: Vec<&Section> = Vec::new();
    let mut merge_len: usize = 0;
    let mut buffer_page_end: Option<usize> = None;

    for leaf in leaves {
        let leaf_text = format!("{}\n{}", leaf.title, leaf.body_text);
        let leaf_len = leaf_text.chars().count();

        if leaf_len < config.merge_min_len {
            // 页面间隙过大 → 先消化当前缓冲区
            if let Some(buf_end) = buffer_page_end {
                let page_gap = leaf.body_page_start.saturating_sub(buf_end);
                if page_gap > MAX_MERGE_PAGE_GAP {
                    flush_merge_buffer(&merge_buffer, parent_path, config, chunks);
                    merge_buffer.clear(); merge_len = 0;
                    buffer_page_end = None;
                }
            }
            merge_buffer.push(*leaf);
            merge_len += leaf_len;
            buffer_page_end = Some(
                buffer_page_end.unwrap_or(leaf.body_page_start)
                    .max(leaf.body_page_end),
            );
            // 合并后过长 → 先消化当前缓冲区
            if merge_len > config.split_max_len {
                flush_merge_buffer(&merge_buffer, parent_path, config, chunks);
                merge_buffer.clear(); merge_len = 0;
                buffer_page_end = None;
            }
        } else {
            // 够长 → 先消化缓冲区，再单独成 chunk
            flush_merge_buffer(&merge_buffer, parent_path, config, chunks);
            merge_buffer.clear(); merge_len = 0;
            buffer_page_end = None;
            // 单独成 Leaf chunk（可能过长触发规则4）
            try_chunk_leaf(leaf, parent_path, config, chunks);
        }
    }
    flush_merge_buffer(&merge_buffer, parent_path, config, chunks);
}
```

`flush_merge_buffer` 使用**锚点式 page 范围上限**：从第一个 leaf 的 page 开始，仅当后续 leaf 与当前范围间隙 ≤ `MAX_MERGE_PAGE_GAP` 时才扩展 page_end，防止远距离格式模板页撑大 chunk 的 page span（如 33→76）。

```
示例:
L4: 1.项目地点：东莞理工学院松山湖校区6号教学楼。  ← 41 字
L4: 2.项目工期：合同签订后 60 个日历日内完成。      ← 35 字
L4: 3.质保期：项目验收合格之日起 2 年。             ← 30 字
L4: 4.完工后，成交供应商需提供竣工图纸。            ← 47 字

→ 合并为 1 个 chunk (~150 字):
    chunk_type: Merged { rule: "adjacent_merge", child_count: 4 }
```

### 4.8 规则 4 — 过长 chunk 在段落边界硬切，安全 overlap

单个 chunk > `split_max_len`（1500 字）→ 找段落边界切开，前后保留 200 字 overlap。

**段落边界检测**（`find_para_boundaries`）：
- `\n\n` — 显式段落分隔
- `\n\n|` 模式 — Markdown 表格行前的空行（确保不切入表格内部）
- `|\n\n` 模式 — Markdown 表格行后的空行
- `\n` 后紧跟中文序号（一～十）— 新段落开始

**安全 overlap 起点搜索**（`find_safe_overlap_start`）：在 overlap 窗口内按优先级查找：
1. 句末标点（。！？）后紧跟换行 → 句子边界
2. `\n\n` → 段落边界
3. `\n` 后跟编号（中文数字/括号/ASCII 数字）→ 语义单元边界
4. 任意换行（最后手段）

找不到安全断点时回退到 `split_point - overlap`。

**死循环保护**：迭代计数上限 `total/50 + 2`，多级 pos 推进检查确保每次迭代向前推进。

```rust
fn split_long_chunk(
    path: &[String], text: &str,
    section: &Section, config: &ChunkingConfig, chunks: &mut Vec<Chunk>,
) {
    let total = text.chars().count();
    let boundaries = find_para_boundaries(text);
    let max_iterations = (total / 50).max(2) + 2; // 安全阀

    let mut parts: Vec<String> = Vec::new();
    let mut pos = 0;
    let mut iteration = 0;

    while pos < total {
        iteration += 1;
        if iteration > max_iterations {
            parts.push(text.chars().skip(pos).collect());
            break;
        }
        let prev_pos = pos;
        let end_candidate = (pos + config.split_max_len).min(total);
        if end_candidate >= total {
            parts.push(text.chars().skip(pos).collect());
            break;
        }
        // 回退到最近的段落边界
        let split_point = boundaries.iter().rev()
            .find(|&&b| b > pos && b <= end_candidate)
            .copied().unwrap_or(end_candidate);
        parts.push(text.chars().skip(pos).take(split_point - pos).collect());

        // 在 overlap 窗口内搜索安全起点（非机械回退）
        let safe_start = find_safe_overlap_start(text, split_point, config.split_overlap);
        pos = if safe_start >= split_point { split_point } else { safe_start };
        if pos <= prev_pos { pos = split_point; } // 最终安全阀
    }

    for (i, part) in parts.iter().enumerate() {
        chunks.push(Chunk {
            chunk_type: ChunkType::Split { part: i + 1, total: parts.len() },
            section_path: path.to_vec(),
            text: part.clone(),
            page_start: section.body_page_start,
            page_end: section.body_page_end,
            source_block_ids: section.block_ids.clone(),
        });
    }
}
```

### 4.9 规则 5 — 嵌入文本携带层级上下文（含标题截断）

向量嵌入时携带层级前缀，避免不同章节的编号条目在向量空间中混淆。支持路径标题截断，防止超长标题撑大嵌入文本：

```rust
impl Chunk {
    /// 生成带层级上下文的嵌入文本。
    /// ctx_depth: 取 section_path 最后 N 级作为前缀
    /// max_path_len: 单个路径元素最大字符数（0 = 不截断）
    ///
    /// 裸文本:  "1）具有独立承担民事责任的能力..."
    /// 嵌入文本: "【供应商的资格要求 > 政府采购法第二十二条】
    ///           1）具有独立承担民事责任的能力..."
    pub fn embed_text(&self, ctx_depth: usize, max_path_len: usize) -> String {
        let ctx = self.section_path.iter().rev().take(ctx_depth).rev()
            .map(|t| truncate_path_title(t, max_path_len))
            .collect::<Vec<_>>().join(" > ");
        if ctx.is_empty() { self.text.clone() }
        else { format!("【{}】\n{}", ctx, self.text) }
    }
}

/// 截断过长的路径标题。
fn truncate_path_title(title: &str, max_len: usize) -> String {
    if max_len == 0 || title.chars().count() <= max_len {
        title.to_string()
    } else {
        let truncated: String = title.chars().take(max_len).collect();
        format!("{}…", truncated)
    }
}
```

Agent 用 `search_document("资格条件 独立承担")` 搜索时，能精确命中这条，而不会误匹配到其他章节的 `"1）..."` 编号条目。

### 4.10 后处理：碎片合并与精确去重

#### Phase 1 — `merge_tiny_chunks`：碎片 chunk 合并

常量 `MAX_MERGE_PAGE_GAP: usize = 2` — 合并时允许的最大页面间隙。

两阶段策略：
- **Pass 1（前向合并）**：将 < `min_chunk_size`（50 字）的碎片合并到前一个相邻 chunk
- **Pass 2（后向合并）**：对 Pass 1 未能合并的碎片，尝试合并到后一个相邻 chunk

合并前检查 `same_parent()`：两个 chunk 共享同一顶级章节（第一位路径元素匹配）即可合并。原先要求全路径一致，放宽到 top-1 匹配后，原先因父路径不同而无法合并的孤立极小 chunk（如评标标准碎片、法律条款碎片）可被正确吸收。

**页面范围膨胀控制**：使用 anchor 追踪机制——对比 anchor 的**原始** page 范围（首次 tiny_merge 之前的 page_end / page_start）。仅当 gap ≤ `MAX_MERGE_PAGE_GAP`（2 页）时才扩展 page 范围。关键设计是对比 anchor 的原始范围而非逐步扩展后的值，防止链式合并逐页推进最终膨胀到数十页。

#### Phase 2 — `dedup_chunks`：精确去重

使用文本内容的 HashSet 进行高效去重。保留第一个出现的 chunk（页面顺序），移除后续重复项。对极短文本（< 20 字符）不执行去重，避免误删不同的短标题。

### 4.11 切分决策总览

| 条件 | 规则 | 动作 |
|------|------|------|
| `body_text` 非空 + 无子节点 + 长度 ≤ 1500 | 规则1 | → `Leaf` chunk |
| `body_text` 非空 + 无子节点 + 长度 > 1500 | 规则1→规则4 | → `Split` chunks (安全 overlap) |
| `body_text` 非空 + 有子节点（容器引言） | 规则1.5 | → `Leaf` chunk (精确 body 页范围) |
| `body_text` 为空 + 无子节点 + 标题非空 | 占位处理 | → 最小 Leaf (后被 tiny_merge 合并) |
| `body_text` 为空 + 有子节点 | 规则2 | → 向下传递路径，分区子节点 |
| 子节点中的多个短叶子 | 规则3 | → `Merged` chunk (含 page gap 控制) |
| 碎片 chunk (< min_chunk_size) | 后处理1 | → 前向/后向合并到相邻 chunk |
| 文本内容完全相同的 chunk | 后处理2 | → 移除重复项 |
| 所有 chunk | 规则5 | → `embed_text()` 携带层级前缀 |

### 4.12 树遍历骨架

```rust
fn traverse_and_chunk(
    section: &Section, parent_path: &Vec<String>,
    config: &ChunkingConfig, chunks: &mut Vec<Chunk>,
) {
    // 规则1: 自包含叶子 → 直接成 chunk（可能触发规则4硬切）
    if try_chunk_leaf(section, parent_path, config, chunks) { return; }

    let mut new_path = parent_path.clone();
    new_path.push(section.title.clone());

    // 纯标题占位（无 body_text 且无子节点）→ 生成最小 Leaf chunk
    if section.children.is_empty() {
        if !section.title.trim().is_empty() {
            chunks.push(Chunk { /* minimal Leaf, 后被 tiny_merge 合并 */ });
        }
        return;
    }

    // 规则1.5: 容器节点自身 body_text → 单独生成 chunk
    if !section.body_text.is_empty() {
        let text = format!("{}\n{}", section.title, section.body_text);
        if text.chars().count() > config.split_max_len {
            split_long_chunk(&new_path, &text, section, config, chunks);
        } else {
            chunks.push(Chunk { /* Leaf with body_page_start/end */ });
        }
    }

    // 规则2: 分离叶子和容器子节点
    let (leaves, containers): (Vec<&Section>, Vec<&Section>) = section.children
        .iter()
        .partition(|c| c.children.is_empty() && !c.body_text.is_empty());

    // 规则3: 相邻独立叶子 → 合并（含页面间隙控制）
    if !leaves.is_empty() {
        merge_adjacent_leaves(&leaves, &new_path, config, chunks);
    }

    // 容器子节点 → 递归处理
    for child in &containers {
        traverse_and_chunk(child, &new_path, config, chunks);
    }
}
```


| 维度 | 代码规则切分 | LLM 方案 |
|------|------------|----------|

### 5.2 模型选型：为什么是 BGE-M3？

标书文件混合了技术规格、资格条件、评分标准、合同条款，语言是正式商务中文 + 技术术语。选择 BGE-M3 基于以下分析：

| 候选模型 | C-MTEB | 上下文窗口 | 输出维度 | 稀疏检索 | 本地部署 | 结论 |
|----------|--------|-----------|---------|---------|---------|------|
| **BGE-M3** 🥇 | 顶级 | 8192 | 1024 | ✅ dense+sparse+ColBERT | ✅ ONNX Q4 | **最佳** |
| Qwen3-Embedding:0.6b | 64.33 | 32K | 1024 | ❌ dense only | ✅ | 轻量备选 |
| mxbai-embed-large ❌ | 无 C-MTEB | 512 | 1024 | ❌ | ✅ | **排除** |

**mxbai-embed-large 排除理由**：训练数据以英文为主，C-MTEB 中文基准无公开分数。某篇被引用的"法律文本 100% 准确率"结论来自英文法规数据集，与中文标书无关。

**BGE-M3 五个入选理由**：

1. **中文最优**：C-MTEB（中文嵌入评测）2025 年检索任务排名第一，在中文法律/政务类文本（与标书语言高度重叠）上表现最佳
2. **8192 token 上下文**：远超标书 chunk（~1500 字 ≈ 3000 tokens），杜绝截断
3. **密集 + 稀疏双表示融合**：dense 1024d 捕获语义，sparse Lexical 匹配精确术语（"质保期"、"违约责任" 等法律用语不会被近义词稀释），评分公式 `0.9*dense + 0.1*sparse`
4. **MIT 开源**：无商业授权顾虑
5. **Q4 量化 ONNX 模型**：568MB 磁盘，CPU 推理 < 200ms/batch（161 chunks），无 GPU 需求

### 5.5 embed_chunks 核心流程

`embed_chunks()` 将 Chunk 列表转化为可搜索的向量索引，四步走：

```rust
// src/services/embedding_service.rs

pub fn embed_chunks(
    chunks: &[Chunk],
    config: &ChunkingConfig,
    document_id: &str,
) -> Result<DocumentVectorIndex> {
    // 1. 生成 embed_text — 每个 chunk 携带层级前缀（§4 规则5）
    let texts: Vec<String> = chunks
        .iter()
        .map(|c| c.embed_text(config.embed_ctx_depth, config.embed_path_max_len))
        .collect();

    // 2. 加载 BGE-M3 量化模型（首次自动下载到 models/）
    let options = Bgem3InitOptions::default()
        .with_cache_dir(PathBuf::from("models"));
    let mut model = Bgem3Embedding::try_new(options)?;

    // 3. 批量编码 — 一次前向传播处理全部 chunk
    let output = model.embed(texts.iter().map(|s| s.as_str()).collect(), None)?;
    //   output.dense: Vec<Vec<f32>> — 每行 1024 维

    // 4. 构建 DocumentVectorIndex → L2 归一化 → 可搜索
    let index = DocumentVectorIndex::new(metas, output.dense);
    Ok(index)
}
```

### 5.6 L2 归一化设计

存储时归一化 → 搜索时内积 = 余弦相似度。这是经典向量检索优化：省去每次搜索时计算两个向量的 L2 范数再相除的开销。

```rust
// src/domain/vector_index.rs — DocumentVectorIndex::new()

impl DocumentVectorIndex {
    pub fn new(chunks: Vec<ChunkMeta>, embeddings: Vec<Vec<f32>>) -> Self {
        let embeddings: Vec<Vec<f32>> = embeddings
            .into_iter()
            .map(|v| {
                let norm: f32 = v.iter().map(|x| x * x).sum::<f32>().sqrt();
                if norm > 0.0 {
                    v.into_iter().map(|x| x / norm).collect()  // 归一化到单位球面
                } else {
                    v  // 零向量保留（不应出现，但防御性处理）
                }
            })
            .collect();
        Self { document_id: String::new(), chunks, embeddings }
    }
}
```

**数学等价性**：

```
cos(u, v) = (u·v) / (||u|| × ||v||)

当 ||u|| = ||v|| = 1 时:
  cos(u, v) = u·v  → 直接内积，无需除法
```

### 5.7 暴力 KNN 搜索

对于 ~200 chunks × 1024d 的规模，暴力点积比构建 ANN 索引（如 HNSW）更快且无近似误差。ANN 的图结构构建开销 ≥ 暴力扫描开销，反而得不偿失。

```rust
// src/domain/vector_index.rs — DocumentVectorIndex::search()

pub fn search(&self, query_embedding: &[f32], top_k: usize) -> Vec<SearchHit> {
    // 1. L2 归一化 query（防御性，如已归一化则几乎无开销）
    let query: Vec<f32> = /* normalize query_embedding */;

    // 2. 暴力余弦相似度 — 全量内积 → 一次扫描
    let mut scored: Vec<(usize, f32)> = self.embeddings
        .iter().enumerate()
        .map(|(i, emb)| {
            let score = emb.iter().zip(&query).map(|(a, b)| a * b).sum();
            (i, score)
        })
        .collect();

    // 3. Top-K via partial sort — O(N log K) 而非 O(N log N)
    scored.sort_unstable_by(|a, b| b.1.partial_cmp(&a.1).unwrap_or(Ordering::Equal));
    scored.truncate(top_k);

    // 4. 组装 SearchHit（含 snippet、title、page_start）
    scored.into_iter().map(|(i, score)| {
        let chunk = &self.chunks[i];
        SearchHit {
            chunk_id: chunk.chunk_id.clone(),
            title: chunk.section_path.last().cloned().unwrap_or_default(),
            score,
            snippet: chunk.embed_text.chars().take(200).collect(),
            page_start: chunk.page_start,
        }
    }).collect()
}
```

**性能分析**：

| 指标 | 数值 |
|------|------|
| 索引规模 | ~100-200 chunks |
| 向量维度 | 1024 (BGE-M3 dense) |
| 内存占用 | ~0.8 MB |
| 单次搜索耗时 | < 0.5 ms |
| 搜索精度 | 100%（暴力全量 = 精确 Top-K） |

> **为什么不用 Qdrant/HNSW？** `search_document` 只搜当前一份标书（~100-200 chunks）。ANN 索引的图结构构建开销（建图 > 插入节点 > 多层导航）在这种规模下远高于直接扫描。当知识库搜索（`web_search`）涉及数万条法规+案例时，才需要 Qdrant。

### 5.8 序列化：保存与加载

### 5.10 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 推理框架 | fastembed-rs (ONNX Runtime) | 纯 Rust 进程内推理，无外部服务依赖 |

| 向量索引 | 内存暴力 KNN | 200 chunks × 1024d 规模，ANN 建图开销 > 扫描开销 |
| 相似度计算 | L2 归一化 → 内积 = cos | 存储时一次性归一化，搜索时只做点积 |
| 序列化 | JSON 元数据 + f32 LE 二进制 | 元数据可读 + 向量矩阵零序列化开销 |
| 批量编码 | 全部 chunk 一次性传入 | fastembed 内部批处理优化，比逐条快 10-20 倍 |
| 模型缓存 | `models/` 目录（项目本地） | 避免污染系统缓存，项目可整体打包迁移 |

### 6.3 核心类型

#### RiskTier — 条款风险分级（零 LLM 成本）

在 Coordinator 路由前通过关键词扫描自动分级，决定 max_turns 和路由策略：

```rust
pub enum RiskTier {
    Low,     // L1: 纯信息/格式条款。触发词：格式、装订、密封、签字、盖章 …
    Medium,  // L2: 标准审查。L1/L3 都不匹配时默认
    High,    // L3: 高风险条款。触发词：品牌、型号、专利、原厂、本地、排他、唯一 …
}
```

| 分级 | max_turns | 触发词类别 | 路由策略 |
|------|-----------|-----------|----------|
| L1 | 8 | 格式/装订/密封/签字/盖章/份数/封面/采购项目编号/磋商邀请 | 仅 FactCheckAgent |
| L2 | 12 | 默认（不匹配 L1/L3） | 按路由矩阵分配 |
| L3 | 14 | 品牌/型号/指定/专利/原厂/本地/地域/排他/唯一/★ | 深度 ReAct，多 Agent 交叉验证 |

> **与设计文档的差异**：设计文档原始值为 L1=2 / L2=6 / L3=12。实际使用中发现审查轮次不够——搜索 + 分析需要多轮交互——大幅上调到当前值。L1 上调最激进（2→8），因"格式/信息"条款实际审查时 Agent 仍需至少 1 轮 read_section + 1-2 轮分析。

分级支持动态升降级：`ReActLoop::check_tier_escalation()` 在 turn 2 检查 Agent 是否表达了高风险怀疑（"可能存在"/"值得深挖"/"疑似"），自动升级 L1→L3 或 L2→L3。

#### ReviewClause — 最小审查单元

一条 ReviewClause 对应一个 Chunk，携带审查所需的所有上下文：

```rust
pub struct ReviewClause {
    pub chunk_id: String,              // "ch_042"
    pub section_path: Vec<String>,     // 从根章节到当前节点的标题链
    pub text: String,                  // 条款完整文本（含标题行，= embed_text() 输出）
    pub page_start: usize,             // 起始页码 (0-based)
    pub page_end: usize,               // 结束页码 (0-based)
    pub tier: RiskTier,                // 关键词扫描分级
    pub tier_max_turns: usize,         // 该级别的最大 ReAct 轮次
}
```

`ReviewClause::from_chunk(chunk, ctx_depth, path_max_len)` 自动执行关键词扫描分级，`effective_max_turns(agent_default)` 取条款级限制与 Agent 默认值的较小值。

#### RiskFinding — 结构化风险发现

Agent `output_finding` 工具输出的完整审查结论，每个字段都有明确用途：

```rust
pub struct RiskFinding {
    pub risk_id: String,            // "R_001"
    pub clause_ids: Vec<String>,    // 关联条款（支持跨条款组合风险）
    pub agent: String,              // 输出 Agent 名称
    pub no_risk: bool,              // true = 合规
    pub severity: RiskSeverity,     // high / medium / low / info
    pub risk_type: String,          // "地域歧视" / "品牌指定" / "程序违规" / …
    pub source_quote: String,       // 从 read_section 返回的原文逐字摘录
    pub legal_basis: Vec<String>,   // ["《政府采购法》第5条", …]
    pub case_refs: Vec<String>,     // 案例引用 ID 列表（如 "case_001"）
    pub reason: String,             // 完整推理链（读了什么→搜了什么→为什么这样判）
    pub suggestion: String,         // 修改建议
    pub confidence: f32,            // [0.0, 1.0]
    // 分级追踪（_ 前缀字段不进入 Agent 的输出 schema）
    pub initial_tier: RiskTier,     // 审查开始时的分级
    pub final_tier: RiskTier,       // 审查结束时的分级
    pub tier_escalated: bool,       // 是否发生过动态升级
    pub truncated: bool,            // 是否因 max_turns 耗尽截断
    // Phase 2 新增字段
    pub suggested_agent: Option<SuggestedAgent>,  // BlindSpot 建议生成的新 Agent

}
```

- `truncated_finding()` — max_turns 耗尽强制输出（confidence=0.3，需人工复核）

**并发控制 — SearchBuffer 缓冲池**（[`search_knowledge.rs`](../src/agents/tools/search_knowledge.rs)）：

多 Agent 并发审查场景下，`SearchBuffer` 将跨 Agent 的搜索请求合并到单后台 worker 串行执行：

```
Agent A ─┐

Agent E ─┘   │ · 单 worker 串行消费   │
             │ · 空结果退避重试(2s)   │
```

**结果过滤**（`is_relevant_result()`）：
- 黑名单域名剔除：`google.com/accounts`、`apple.com`、`reddit.com` 等
- 语言过滤：纯英文 snippet 且不含政务关键词 → 丢弃
- 最小长度：snippet < 10 字符 → 丢弃

##### 技术选型理由

选择 DashScope 原生 API 而非继续深耕 SearXNG 的原因：

- **并发自由**：不再需要 SearchBuffer 串行队列——每个 Agent 独立调 API，无锁无排队
- **回答质量**：模型综合搜索结果生成分析结论 + 引用标注，而非丢给 Agent 自己读链接
- **轮次节省**：Agent 1 轮拿到结论 vs 旧模式 2-3 轮（搜→读→推理），审查速度提升 2-3 倍
- **零运维**：无需 Docker、无需搜索引擎配置、无需处理 CAPTCHA/GFW/结果质量
- **SearXNG 保留为回退**：`KnowledgeSearch` trait 和 `SearchBuffer` 完整保留，一键切换

```rust
}
```

**低相似度警告**：所有命中 score < 0.5 时自动附加 `warning` 字段，提示 Agent 换搜索词。

#### 工具 3: `read_section` — 条款原文精读

按 `chunk_id` 在 `Arc<HashMap<String, Chunk>>` 上做 O(1) 查找，返回完整条款文本 + 页码 + 父章节路径。支持单个读取或数组批量读取。

**设计原则**：这是 Agent 获取条款全文的唯一工具——Agent 初始收到的可能只是摘要，需要精读原文确认证据时必须用这个工具。`source_quote` 必须从 `read_section` 返回的原文中逐字截取。

#### 工具 4: `output_finding` — 终端工具

Agent 调用此工具表示证据充分，可以下结论。这是 ReAct 循环的退出信号——`ReActLoop` 检测到 `tool_call.name == "output_finding"` 后立即退出循环，返回 `RiskFinding`。

工具实现本身是透传：LLM 传入的 arguments 就是 `RiskFinding` 的 JSON，`ReActLoop` 从中解析并补充分级追踪字段。

### 6.5 ReAct 循环引擎

`ReActLoop` 是 Agent 框架的运行时核心，定义在 [`src/agents/react_loop.rs`](../src/agents/react_loop.rs)。

#### LLM 客户端抽象

```rust
#[async_trait]
pub trait LlmClient: Send + Sync {
    async fn chat(&self, messages: &[ChatMessage], tools: &[serde_json::Value])
        -> Result<LlmResponse>;
}
```

`LlmClient` trait 解耦 ReAct 循环与具体 LLM 提供商。MVP 提供 `OpenAICompatibleClient` 实现——基于 `reqwest` 直接调用 OpenAI Chat Completions API（或任何兼容端点），不依赖 `async-openai` crate。

`OpenAICompatibleClient::from_env()` 从以下环境变量读取配置：

| 环境变量 | 用途 | 默认值 |
|----------|------|--------|
| `OPENAI_API_KEY` | API 密钥 | 必须设置 |
| `OPENAI_BASE_URL` | API 端点 | `https://api.openai.com/v1` |
| `LLM_MODEL` | 模型名称 | `gpt-4o` |

#### 核心循环（单条款）

```
对于每条 ReviewClause:
  conversation = [system_prompt, user(clause_text + tier_hint)]

  while turn < max_turns:
    turn++

    ① Poll AgentBus → 注入其他 Agent 的高风险广播消息
    ② LLM 推理 → llm.chat(conversation, tool_defs)
    ③ 检查 output_finding → 有 → 解析 RiskFinding，退出循环
    ④ 执行工具调用 → 追加 tool results 到 conversation
       · web_search → 走 ReActLoop 缓存层
       · 空搜索检测 → 连续 2 次空结果 → 提示 Agent 换策略
    ⑤ turn=2 → 动态升降级检测

  max_turns 耗尽 → 强制输出 truncated_finding (confidence=0.3)
```

**条款级分级提示**：`format_clause_prompt()` 根据 tier 注入不同的审查提示：

- **L1**: "此条款为格式/信息类，风险极低。请在 1-2 轮内提取关键事实、与阈值对照后输出结论"
- **L2**: "请按标准流程审查：精读条款 → 搜索法规 → 搜索案例（如需要）→ 输出结论"
- **L3**: "此条款含高风险关键词（品牌/地域/排他性），请深度审查"

**动态升降级**：`check_tier_escalation()` 在 turn 2 扫描 Agent 的 assistant 消息，检测可疑短语（"可能存在"/"值得深挖"/"疑似"/"涉嫌"/"潜在风险"等），自动升级 L1/L2 → L3；L3 无信号则降级到 L2。

**搜索缓存**：`cached_web_search()` 在 `ReActLoop` 层维护 `(question, search_context)` 缓存 HashMap，同一 Agent 内相同查询不重复调用搜索后端。

**空搜索治理**：连续 2 次搜索结果为空 → 注入 system 提示"换搜索词、换 category，或基于已有信息直接输出结论——不要钻牛角尖"。

#### 关键设计：ReAct 循环为什么不由 LLM 控制？

LLM 在 `while` 循环内——每次迭代由 Rust 代码调用 LLM，LLM 只输出下一轮的工具调用，不控制循环次数。`max_turns` 是硬上限，由条款的 `RiskTier` 决定（L1=2, L2=6, L3=12）。

```text
for turn in range(MAX_TURNS):      // ← Rust 代码在循环（硬上限）
    response = llm.chat(conversation, tools=[...])
    if response.has_tool_call("output_finding"):
        return risk_finding          // Agent 认为证据够了，主动输出
    // 否则执行工具调用，结果追加到对话历史，继续下一轮
// max_turns 耗尽 → 强制输出 truncated finding
```

### 6.8 AgentBus — Agent 间广播通道

定义在 [`src/agents/bus.rs`](../src/agents/bus.rs)。设计文档 §7.9 定义：只广播 severity=high 的发现，避免噪音。

**Phase 2 增强实现**：

- **`BusMessage` 字段扩展**：`from` 从 `String` 改为 `AgentId` 枚举；新增 `target`（Broadcast/Direct）、`topic`（RiskFound/CrossReference）、`clause_ids`、`risk_type` 字段
- **`subscribe()` 方法**：Agent 获取专属 `Receiver<BusMessage>`，在 ReActLoop 初始化时持有，每轮 `try_recv()` 循环排空——解决原 `poll_since()` 每次创建新 subscriber 丢消息的 bug
- **`poll_since()` 保留**：仅向后兼容，标注为"每次创建新 subscriber，多 Agent 并发下可能丢消息"
- **severity 过滤**：`broadcast()` 自动过滤非 High 消息——Medium/Low/Info 不进入广播

**使用**：在 ReAct 循环的每轮开始时，Agent 通过持久 `bus_rx` 排空所有积压消息。如果有其他 Agent 的高风险发现，注入 `[AgentBus]` system 消息提示做交叉验证。

### 6.10 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 风险分级 | 关键词扫描（零 LLM 成本） | 中文标书关键词高度特征化，正则匹配 100% 覆盖 |
| LLM 角色 | while 循环内被调用，不控制循环 | Rust 硬上限 max_turns，LLM 只输出工具调用 |
| LLM 客户端 | reqwest 直调 OpenAI API | 零 crate 依赖，无 async-openai 类型开销 |
| 工具接口 | AgentTool trait + ToolRegistry | 统一接口 + O(1) 查找，新增工具无需修改 ReAct 循环 |
| 搜索后端 | DashScope（默认）/ SearXNG（回退）双模式 | DashScope 零运维+无限并发，SearXNG $0 回退 |
| 缓存策略 | ReActLoop 层 (question, search_context) 缓存 | 避免修改 SearchKnowledgeTool 的内部可变性 |
| Agent 通信 | AgentBus（推）+ SessionGraph（拉）双通道 | 推拉互补：推送通知，拉取查询完整上下文 |
| LLM 实例化 | 工厂函数（llm_factory + tools_factory） | 避免 clone_box 传染到 LlmClient/AgentTool/ToolRegistry |
| Agent 定义 | 数据驱动（AgentDefinition + AgentRegistry） | 新增 Agent 只需加一行注册 + 一个 prompt 常量 |
| 追溯日志 | 内存收集 → JSONL flush | MVP 够用，Phase 3 扩展为流式写入 |
| 审查范围 | MVP 默认 5 条条款 | 快速验证框架可用性，通过环境变量可调 |
| 动态 Agent | BlindSpot suggest_agent → dynamic_agents.json → 下次加载 | 运行时发现新审查维度，持久化到下次 Session 复用 |

```rust
}
```

**`subscribe()` 动机**：原 `poll_since()` 每次创建新的 `broadcast::Receiver`，只能收到订阅之后的消息——Agent A turn 1 的广播，Agent B turn 2 收不到。`subscribe()` 返回持久 Receiver，Agent 在 ReActLoop 初始化时持有，每轮 `try_recv()` 排空所有积压消息。

### 7.5 Coordinator：10 步聚合流水线

实际流水线比设计文档多 4 步：

```
[1] ROUTE          → clauses → HashMap<AgentId, Vec<ReviewClause>>
                      ★ 空关键词的 Agent (BlindSpot/LegalVerify/Debate) 不参与路由
                      ★ 无匹配的条款 fallback 到 FactCheckAgent

[2] PRELOAD_CHUNKS → 所有 Chunk 节点写入 SessionGraph

[2b] PRELOAD_AGENTS → 所有启用的 Agent 节点写入 SessionGraph（含 role 属性）

[3] EXECUTE         → tokio::spawn × N agents 并行执行
                      ★ 每个 Agent: llm_factory() + tools_factory() → 独立客户端
                      ★ Agent 审查完成后自动写入 SessionGraph + AgentBus 广播

[4] MERGE           → 按 (risk_type, clause_ids, agent) 去重，保留高 confidence

[4b] LINK  ★新      → derive_cross_agent_links():
                      按 risk_type 分组 → 不同 Agent 发现同类型风险 
                      → 在 clause_ids 之间自动创建 linked_to 边

[5] LEGAL_VERIFY    → 收集有 legal_basis 的 findings → 格式化为批量验证任务
                      → 启动 LegalVerifyAgent ReAct（独立 LLM 客户端，不接入 Bus/Graph）
                      → 验证结果合并回原 findings

[6] BLINDSPOT       → 获取 GraphSnapshot → 候选条款筛选
                      (跳过 L1 + frontmatter + reviewed>1且有风险发现)
                      → 构建图上下文附录 → 启动 BlindSpotAgent ReAct
                      → ReAct 失败/无产出 → fallback 到 blind_spot_fallback()

[6.5] DEBATE ★新    → 筛选 High + confidence<0.85 的发现 → 逐条启动 DebateAgent
                      → Defender/Challenger/Arbiter 裁决 → 更新原 finding

[6.6] REGISTER ★新  → 扫描 findings 中的 suggested_agent → 去重(Jaccard>0.5)
                      → 写入 agents/dynamic_agents.json (上限20, active=false)

[7] TRIAGE          → 按 severity 降序 + confidence 降序排列
```

### 7.6 动态 Agent 生命周期

BlindSpotAgent 的 system prompt 中定义了 `suggest_agent` 机制——当发现遗漏模式且现有 7 个 Reviewer 的审查范围不覆盖时，可在 `output_finding` 中附带 `suggested_agent` 字段。

**完整生命周期**：

```
BlindSpot 审查 → output_finding 含 suggested_agent
  → Coordinator.register_dynamic_agents() 扫描 findings
    → 校验: agent_prompt 非空 && section_keywords 非空
    → 去重: is_duplicate_dynamic_agent() Jaccard 重叠度 > 0.5 → 跳过
    → 写入 agents/dynamic_agents.json（active=false，上限20个，超出入队淘汰）
    → JSON 中 stored but NOT active（需人工审批）

下次 Session:
  → Coordinator::new() → load_dynamic_agents()
    → 读取 dynamic_agents.json，active=true 的加载到 registry + enabled_agents
    → 路由时使用 DynamicAgent 的 section_keywords 匹配条款文本
```

### 7.8 关键设计决策（更新）

| 决策 | 选择 | 理由 |
|------|------|------|
| Agent 数量 | 10 内置 + Dynamic | 将 LegalVerify 和 Debate 从 Coordinator 逻辑独立为 Agent，统一 ReAct 接口 |
| LegalVerify 独立化 | 独立 Agent 而非 Coordinator 方法 | ReAct 循环提供搜索/验证能力，比硬编码 fallback 更准确 |
| DebateAgent 独立化 | 独立 Agent + 三角色框架 | Defender/Challenger/Arbiter 在一个 ReAct 内完成，LLM 自主切换角色 |
| 动态 Agent | BlindSpot suggest_agent 机制 | 运行时发现新审查维度，持久化到下次 Session 复用；人工审批 gate (active=false) |
| Coordinator 管线 | 从 6→10 步 | Link+Register 是确定性操作，零 LLM 成本；Debate 按需触发，非全局 |
| RiskTier max_turns | L1=8, L2=12, L3=14 | 实际审查中搜索+分析需要多轮交互，原始值导致过早截断 |
| Agent max_turns | 全面上调 | 同上；FactCheck 从 4→10 是最大跳跃（L1 条款也需 1 轮 read + 1-2 轮分析） |
| SessionGraph 扩展 | +contradicts/same_law/agents/laws/cases | 支持矛盾检测、同法条关联推导、Agent/Law/Case 节点预写入 |
| AgentBus 扩展 | +subscribe() + MessageTarget/MessageTopic | 解决 broadcast 丢消息 bug；为未来定向消息和主题订阅预留 |

```rust
/// ★ 架构决策：ChatAgent 不继承 ReActLoop。
/// ReActLoop 的输入 (ReviewClause → RiskFinding) 与 ChatAgent 的输入
/// (用户自然语言 → ChatResponse) 类型根本不同。两者共享底层抽象
/// （LlmClient trait / ToolRegistry / ChatMessage / execute_tool_calls helper），
/// 但不共享 ReAct 循环骨架。
///
/// 核心逻辑：
/// 1. 加载 project_config + user_preferences（如存在）
/// 2. 构建带配置注入的 system_prompt
/// 3. 每次 chat() 构建对话（使用 ChatMessage 枚举）→ 简化 ReAct 循环 → 解析 ChatResponse
/// 4. chat_loop() 提供 stdio 交互模式
pub struct ChatAgent {
    pub config: ChatAgentConfig,
    pub project_config_content: String,
    pub user_preferences_content: String,
    /// LLM 客户端（Arc 共享，与批量审查 Agent 复用同一实例）
    pub llm: Arc<dyn LlmClient>,
    /// 工具注册表（含 web_search / search_document / read_section / answer_user）
    pub tools: ToolRegistry,
    /// 可选：SessionGraph 引用（对话结束后摘要写入，Phase 3）
    pub graph: Option<Arc<SessionGraph>>,
}

impl ChatAgent {
    /// 创建 ChatAgent（加载 .ai-bid/ 配置文件）。
    pub fn new(
        config: ChatAgentConfig,
        llm: Arc<dyn LlmClient>,
        tools: ToolRegistry,
    ) -> Result<Self> {
        // 加载 project_config（如存在，不存在为空）
        let project_config_content =
            std::fs::read_to_string(&config.project_config_path).unwrap_or_default();
        // 加载 user_preferences（如存在，不存在为空）
        let user_preferences_content =
            std::fs::read_to_string(&config.preferences_path).unwrap_or_default();

        Ok(Self {
            config,
            project_config_content,
            user_preferences_content,
            llm,
            tools,
            graph: None,
        })
    }

    /// 构建完整的 system_prompt。
    fn build_system_prompt(&self, selection: &Option<TextSelection>) -> String {
        let mut prompt = String::from(CHAT_AGENT_SYSTEM_PROMPT);

        // 注入项目配置
        if !self.project_config_content.is_empty() {
            prompt.push_str("\n\n── 项目审查配置 (review-config.md) ──\n");
            prompt.push_str(&self.project_config_content);
        }

        // 注入用户偏好
        if !self.user_preferences_content.is_empty() {
            prompt.push_str("\n\n── 用户偏好 (user-preferences.md) ──\n");
            prompt.push_str(&self.user_preferences_content);
        }

        // 注入划词上下文
        if let Some(sel) = selection {
            prompt.push_str(&format!(
                "\n\n用户当前在 PDF 第 {} 页选中了以下文字:\n> {}\n(block_ids: {:?})\n你可以在回答中引用 block_id 让前端渲染高亮。",
                sel.page + 1, sel.text, sel.block_ids
            ));
        }

        prompt
    }

    /// 构建用户消息（含 selection 注入）。
    fn build_user_message(&self, selection: &Option<TextSelection>, user_input: &str) -> String {
        if let Some(sel) = selection {
            format!(
                "用户在 PDF 第 {} 页选中了以下文字:\n> {}\n(block_ids: {:?})\n\n用户提问: {}",
                sel.page + 1, sel.text, sel.block_ids,
                if user_input.is_empty() { "请分析这段文字的合规性" } else { user_input }
            )
        } else {
            user_input.to_string()
        }
    }

    /// 单次对话入口。
    ///
    /// * `selection` — PDF 划词内容（可为 None）
    /// * `user_input` — 用户问题（可为空字符串）
    /// * `history` — 同一对话的历史消息（支持追问，使用 ChatMessage 枚举）
    pub async fn chat(
        &self,
        selection: Option<TextSelection>,
        user_input: &str,
        history: Option<Vec<ChatMessage>>,
    ) -> Result<ChatResponse> {
        // ★ 构建对话（使用 ChatMessage 枚举，与 ReActLoop 一致）
        let mut conversation: Vec<ChatMessage> = vec![
            ChatMessage::System {
                content: self.build_system_prompt(&selection),
            },
        ];

        // 追加历史（如有）
        if let Some(h) = history {
            conversation.extend(h);
        }

        conversation.push(ChatMessage::User {
            content: self.build_user_message(&selection, user_input),
        });

        // ── 简化 ReAct 循环 ──
        // ChatAgent 不需要 tier 升级、AgentBus poll、SessionGraph 查询
        // 这些是批量审查特有的逻辑
        let tool_defs = self.tools.definitions();  // ChatAgent 暴露全部工具
        let mut response: Option<LlmResponse> = None;

        for turn in 1..=self.config.max_turns {
            // 最后一轮强制 answer_user
            let tool_choice = if turn == self.config.max_turns {
                ToolChoice::Specific { name: "answer_user".to_string() }
            } else {
                ToolChoice::Auto
            };

            let result = self.llm.chat(&conversation, &tool_defs, &tool_choice).await?;

            // 终止条件 1: LLM 调用 answer_user
            if result.has_answer_user() {
                response = Some(result);
                break;
            }

            // ★ 调用共享的 tool execution helper（与 ReActLoop 共用）
            execute_tool_calls(&result, &self.tools, &mut conversation).await?;

            // 终止条件 2: LLM 直接输出文本（无 tool call，自然对话结束）
            if result.content.is_some() && result.tool_calls.is_empty() {
                response = Some(result);
                break;
            }
        }

        // 解析 ChatResponse
        match response {
            Some(resp) => {
                if let Some(args) = resp.get_answer() {
                    Ok(self.parse_answer_user(args))
                } else {
                    Ok(ChatResponse {
                        answer: resp.content.unwrap_or_default(),
                        references: Vec::new(),
                        knowledge_refs: Vec::new(),
                        confidence: None,
                        suggested_actions: Vec::new(),
                    })
                }
            }
            None => {
                // max_turns 耗尽
                Ok(ChatResponse {
                    answer: "抱歉，我在审查该问题时达到了分析上限。请尝试用更具体的问题重新提问。".to_string(),
                    references: Vec::new(),
                    knowledge_refs: Vec::new(),
                    confidence: None,
                    suggested_actions: vec!["尝试将问题拆分为更小的子问题".to_string()],
                })
            }
        }
    }

    /// 解析 answer_user 参数 → ChatResponse。
    fn parse_answer_user(&self, args: &serde_json::Value) -> ChatResponse {
        let answer = args["answer"].as_str().unwrap_or("").to_string();

        // 从 answer 文本中提取 [b_xxx] 引用构建 BlockRef
        let re = Regex::new(r"\[(b_\d+_\d+)\]").unwrap();
        let references: Vec<BlockRef> = re
            .captures_iter(&answer)
            .map(|cap| BlockRef {
                block_id: cap[1].to_string(),
                quote: String::new(), // 由前端从 block_id 查询
                snippet: String::new(),
                page: 0,
            })
            .collect();

        let knowledge_refs: Vec<KnowledgeRef> = args["knowledge_refs"]
            .as_array()
            .map(|arr| arr.iter().filter_map(|v| serde_json::from_value(v.clone()).ok()).collect())
            .unwrap_or_default();

        let suggested_actions: Vec<String> = args["suggested_actions"]
            .as_array()
            .map(|arr| arr.iter().filter_map(|v| v.as_str().map(String::from)).collect())
            .unwrap_or_default();

        ChatResponse {
            answer,
            references,
            knowledge_refs,
            confidence: args["confidence"].as_f64().map(|c| c as f32),
            suggested_actions,
        }
    }

    /// stdio 交互循环。
    pub async fn chat_loop(&self) -> Result<()> {
        println!();
        println!("═══ ChatAgent 交互模式 ═══");
        println!("输入 /help 查看命令, /quit 退出");
        println!();

        // ★ 对话历史使用 ChatMessage 枚举
        let mut history: Vec<ChatMessage> = Vec::new();

        loop {
            print!("You: ");
            io::stdout().flush()?;

            let mut line = String::new();
            io::stdin().read_line(&mut line)?;
            let line = line.trim().to_string();

            if line.is_empty() { continue; }
            if line == "/quit" || line == "/exit" { break; }
            if line == "/help" {
                println!("  /quit  — 退出对话");
                println!("  /clear — 清除对话历史");
                println!("  直接输入问题开始对话，支持多轮追问");
                continue;
            }
            if line == "/clear" {
                history.clear();
                println!("对话历史已清除");
                continue;
            }

            print!("ChatAgent: ");
            io::stdout().flush()?;

            match self.chat(None, &line, Some(history.clone())).await {
                Ok(response) => {
                    println!("{}", response.answer);
                    // 追加到历史
                    history.push(ChatMessage::User { content: line });
                    history.push(ChatMessage::Assistant {
                        content: Some(response.answer),
                        tool_calls: None,
                    });
                }
                Err(e) => {
                    eprintln!("Error: {:?}", e);
                }
            }
        }
        Ok(())
    }
}
```

> **设计变更（相比初始设计）**：
> - 移除 `llm_factory` / `tools_factory` 工厂闭包 → 改为直接持有 `Arc<dyn LlmClient>` + `ToolRegistry`。LLM 客户端可安全跨线程共享。
> - 移除 `bus` / `trace` 字段。ChatAgent 不参与 AgentBus 广播（单 Agent 对话模式）。
> - 对话格式统一使用 `ChatMessage` 枚举，与 `ReActLoop` 一致。
> - 工具执行逻辑调用共享的 `execute_tool_calls()` helper（从 `ReActLoop` 提取），避免代码重复。
> - `chat_loop()` 历史存储改为 `Vec<ChatMessage>`，不再使用裸 `serde_json::Value`。

### 8.6 System Prompt

```rust
// src/agents/prompts.rs — 新增常量

/// ChatAgent 的 system prompt。
///
/// 与批量审查 Agent 的 system prompt 关键差异：
/// - 角色定位：法律顾问而非审查机器
/// - 工具：answer_user 替代 output_finding
/// - 回答风格：对话式，支持 [b_xxx] 高亮标记
/// - 容错：不确定时坦诚说，不编造
pub const CHAT_AGENT_SYSTEM_PROMPT: &str = r##"你是 AI 招标文件合规审查助手（ChatAgent）。

## 你的角色

你是一位经验丰富的政府采购法律顾问，协助用户分析招标文件的合规性。
你的回答应该像一位知识渊博的同事在与采购专家讨论——专业、准确、坦诚，
而非生硬地朗读法律条文。

## 可用工具

- `web_search(question, search_context)` — 搜索外部知识（法规/案例/负面清单）
- `search_document(query)` — 在当前标书内语义搜索关联条款
- `read_section(chunk_id)` — 精读指定章节的完整原文
- `answer_user(answer, ...)` — 向用户输出最终回答

## 回答原则

1. **引用原文时用 [chunk_id] 标注**：格式为 `[b_3_7]原文片段`，前端会渲染为 PDF 高亮链接
2. **法规引用具体到条、款、项**：不说"根据相关法规"，说"根据《实施条例》第20条(二)"
3. **不确定时坦诚说**：不知道就不知道，不编造法规
4. **发现关联条款时主动告知**：某个资格条件 + 某个评分标准 = 组合排斥，你要说出来
5. **对话式回答**：用户问什么你答什么，不要模板化输出

## 回答格式建议

- 涉及合规判断 → 表格形式（原文 | 问题 | 法规依据 | 建议）
- 纯信息性回答 → 自然段落
- 多个关联问题 → 分点回答

## 搜索策略

1. 涉及具体条款合规 → 先 read_section 理解上下文
2. 需要法规依据 → web_search(question, "法规")
3. 需要案例佐证 → web_search(question, "案例")
4. 需要找关联条款 → search_document(query)
5. 证据充分后 → answer_user 输出回答

## 边界

- 你可以分析合规性、查找法规、提出建议
- 你不能提供法律意见（最终判断由用户和法务团队确认）
- 你不能修改招标文件（只建议如何修改）
"##;
```

### 8.9 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| **ChatAgent 不继承 ReActLoop** | 独立结构体，提取共享 helper | ReActLoop 输入 (ReviewClause→RiskFinding) 与 ChatAgent (NL→ChatResponse) 类型根本不同；强行继承会污染接口 |
| **共享 execute_tool_calls()** | 从 ReActLoop 提取公共 helper | 工具执行 + 对话追加逻辑完全一致，避免代码重复 |
| **Arc<dyn LlmClient>** | 直接持有，不用工厂闭包 | LLM 客户端可安全跨线程共享，工厂闭包引入不必要的装箱开销 |
| answer_user vs output_finding | 独立工具 | 输出格式完全不同（NL vs 结构化 Risk），混用会污染 LLM 判断 |
| 对话历史跨轮累积 | 不按条款清空 | 追问场景需要完整上下文（"b_10_5 的本地业绩加分合规吗？"依赖前轮已读的 b_3_7） |
| **对话格式统一** | ChatMessage 枚举 | 与 ReActLoop 的 LlmClient::chat() trait 签名一致，不使用裸 serde_json::Value |
| review-config.md 注入 | 每次对话启动时全量注入 system_prompt | 对标 Claude Code CLAUDE.md 模式，版本可控 |
| 对话压缩 | **推迟到 Phase 3** | MVP 阶段直接截断保留最近 N 轮；LLM 摘要压缩（保留关键发现丢弃中间推理）实现复杂度高 |
| BlockRef 解析 | 正则提取 `[b_xxx]` | 确定性规则，零 LLM 成本 |
| max_turns = 12 | 高于批量 Agent 默认 | 对话场景常需多轮搜索+确认 |
| save_preference | **推迟到 Phase 3** | MVP 阶段用户手动编辑 .md 文件；Harness 模式匹配 + LLM 协调实现复杂度高 |

### 8.10 与批量审查管线的对照

| 维度 | 批量审查管线（已有） | ChatAgent（新增） |
|------|-------------------|-------------------|

### 8.13 对话持久化 — output/chat/{stem}/

ChatAgent 的每次对话自动持久化到 `output/chat/` 目录，遵循与已有 `raw_json/` / `sections/` / `chunks/` / `embeddings/` / `findings/` 一致的输出约定。

**8.13.1 输出目录结构**

```

├── conv_20260627_143005.json      ← 单次会话完整记录（ChatSession）
├── conv_20260627_151230.json
└── ...
```

**8.13.2 ChatSession 数据模型**

```rust
// src/domain/chat_session.rs — 新增文件

use crate::agents::types::{TextSelection, BlockRef, KnowledgeRef};
use serde::{Deserialize, Serialize};

/// 一次对话会话的完整记录。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ChatSession {
    pub session_id: String,               // "conv_20260627_143005"
    pub document_id: String,              // 关联文档 UUID
    pub document_stem: String,            // 文件名（无后缀）
    pub started_at: String,               // ISO 8601 开始
    pub ended_at: String,                 // ISO 8601 结束

    pub selection: Option<TextSelection>, // 用户划词（如有）
    pub project_config_used: bool,        // review-config.md 是否加载

    pub turns: Vec<ChatTurn>,             // 每轮完整记录
    pub summary: ChatSessionSummary,      // 自动摘要（写入 chat_index.json）
}

/// 单轮对话记录。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ChatTurn {
    pub turn_index: usize,
    pub user_message: String,
    pub assistant_answer: String,         // answer_user 的 answer 字段
    pub confidence: Option<f32>,
    pub tool_calls: Vec<ChatToolCall>,
    pub references: Vec<BlockRef>,
```

```rust
// src/agents/chat_agent.rs — 新增方法

use crate::domain::chat_session::{ChatSession, ChatTurn, ChatToolCall, ChatSessionSummary};

impl ChatAgent {
    /// 带持久化的单次对话。
    ///
    /// 与 chat() 功能相同，额外：
    /// - 记录每轮工具调用耗时和结果摘要
    /// - 对话结束时写入 output/chat/{stem}/conv_{timestamp}.json
    /// - 更新 output/chat/{stem}/chat_index.json
    pub async fn chat_with_persistence(
        &self,
        selection: Option<TextSelection>,
        user_input: &str,
        history: Option<Vec<serde_json::Value>>,
        document_id: &str,
        document_stem: &str,
        output_dir: Option<&str>,
    ) -> Result<ChatResponse> {
        let started_at = chrono::Utc::now();
        let mut tool_calls_log: Vec<ChatToolCall> = Vec::new();

        // ... 执行 chat() 的完整逻辑，逐轮记录工具调用 ...

        let response = self.chat(selection, user_input, history).await?;
        let ended_at = chrono::Utc::now();

        if let Some(dir) = output_dir {
            let session_id = format!("conv_{}", started_at.format("%Y%m%d_%H%M%S"));
            let chat_dir = format!("{}/chat/{}", dir, document_stem);
            std::fs::create_dir_all(&chat_dir)?;

            let session = ChatSession {
                session_id: session_id.clone(),
                document_id: document_id.to_string(),
                document_stem: document_stem.to_string(),
                started_at: started_at.to_rfc3339(),
                ended_at: ended_at.to_rfc3339(),
                selection,
                project_config_used: !self.project_config_content.is_empty(),
                turns: vec![ChatTurn {
                    turn_index: 1,
                    user_message: user_input.to_string(),
                    assistant_answer: response.answer.clone(),
                    confidence: response.confidence,
                    tool_calls: tool_calls_log,
                    references: response.references.clone(),
                    knowledge_refs: response.knowledge_refs.clone(),
                }],
                summary: ChatSessionSummary {
                    session_id: session_id,
                    started_at: started_at.to_rfc3339(),
                    question_count: 1,
                    topics: ChatAgent::extract_topics(user_input, &response.answer),
                    referenced_chunks: response.references.iter().map(|r| r.block_id.clone()).collect(),
                    referenced_laws: response.knowledge_refs.iter().map(|k| k.title.clone()).collect(),
                    has_compliance_judgment: response.confidence.is_some(),
                    max_confidence: response.confidence,
                    total_tool_calls: tool_calls_log.len(),
                    total_duration_ms: (ended_at - started_at).num_milliseconds() as u64,
                },
            };

            // 写入完整记录
            let session_path = format!("{}/{}.json", chat_dir, session.session_id);
            std::fs::write(&session_path, serde_json::to_string_pretty(&session)?)?;

            // 追加摘要到索引
            ChatAgent::append_to_index(&chat_dir, &session.summary)?;
        }

        Ok(response)
    }

    /// 追加会话摘要到 chat_index.json。
    fn append_to_index(chat_dir: &str, summary: &ChatSessionSummary) -> Result<()> {
        let index_path = format!("{}/chat_index.json", chat_dir);
        let mut index: Vec<ChatSessionSummary> = if std::path::Path::new(&index_path).exists() {
            serde_json::from_str(&std::fs::read_to_string(&index_path)?)?
        } else {
            Vec::new()
        };
        index.push(summary.clone());
        std::fs::write(&index_path, serde_json::to_string_pretty(&index)?)?;
        Ok(())
    }

    /// 从用户问题 + 回答中提取话题标签（关键词匹配）。
    fn extract_topics(user_input: &str, answer: &str) -> Vec<String> {
        // 简单关键词匹配；后续可用 LLM 提取
        let combined = format!("{} {}", user_input, answer);
        let mut topics = Vec::new();
        let topic_keywords = [
            ("资格条件", "资格条件"),
            ("地域", "地域限制"),
            ("品牌", "品牌指定"),
            ("评分", "评分标准"),
            ("合同", "合同条款"),
            ("付款", "付款条件"),
            ("保证金", "保证金"),
            ("资质", "资质要求"),
            ("业绩", "业绩要求"),
            ("技术参数", "技术参数"),
        ];
        for (kw, label) in &topic_keywords {
            if combined.contains(kw) {
                topics.push(label.to_string());
            }
        }
        topics.dedup();
        topics
    }
}
```
