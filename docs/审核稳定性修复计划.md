# 审核链路稳定性修复计划（TDD）

> 背景：2026-08-26 `test/ERZHONGYI_mutated` 审核任务卡死 30 分钟。
> 根因：Rust 审核引擎将进行中的审核状态全部放在进程内存；14:40 容器重建导致
> 内存蒸发，Java 侧 SSE 断线且无重连，轮询 `GET /result` 得 404 后盲等 30 分钟超时。
>
> 本文档定义修复项、TDD 测试策略与端到端验收标准。每项修复遵守：
> **先写失败测试 → 实现 → 测试转绿 → 回归全部既有测试**。

---

## 缺陷清单（对应根因分析）

| # | 缺陷 | 位置 | 影响 |
|---|------|------|------|
| D1 | 审核进行态全内存，重启即蒸发，中断不可检测 | Rust `AppState` / `handlers.rs` | 孤儿任务 |
| D2 | Java 对 `failed`/404 结果盲等 30 分钟才失败 | Java `AuditEngineServiceImpl.awaitReviewResult` | 卡死 30 分钟 |
| D3 | 无孤儿任务守护，孤儿永久滞留 PROCESSING | Java（缺失） | 前端永远"审核中" |
| D4 | Java→Rust SSE 客户端一次性连接，无重连 | Java `RustSseClient` | 网络抖动即断 |
| D5 | `startReview` 用 5s 连接超时当整个请求超时 | Java `RustApiClient.startReview` | 误报启动失败 |
| D6 | 运维 update/rollback 重建容器不检查在途审核 | `deploy/update.sh`, `rollback.sh` | 人为制造孤儿 |

---

## 修复方案

### F1（Rust，治本）审核中断状态落盘 + 重启可检测
- 新增 `backend-rust/src/api/review_state.rs`：
  - `ReviewStateFile { status, started_at, updated_at, error }`
  - `write_running(dir, doc_id)` / `write_failed(dir, doc_id, error)` / `remove(dir, doc_id)` / `read(dir, doc_id)`
  - 纯函数 `disk_recovery(tenant_id, doc_id, findings_dir) -> Option<ReviewResultResponse>`
- `POST /review` accepted 后立即写 `{doc_id}_review_state.json`（status=running）。
- 管线完成 → 删除状态文件；管线失败 → 写 status=failed + error。
- `GET /review/:doc_id/result` 查询顺序变为：
  1. 内存结果 → 返回
  2. 内存错误 → 返回 failed
  3. 活跃总线存在 → 返回 pending
  4. 磁盘 result.json → 返回（原兜底）
  5. **磁盘状态文件**：running 且无活跃总线 → 返回 `failed`，
     error=`审核引擎重启导致审核中断，请重新发起审核`；failed → 返回原错误
  6. 404
- 效果：Rust 重启后，Java 下一次轮询（≤3s）即拿到 failed，不再盲等。

### F2（Java）审核等待快速失败并携带真实错误
- `awaitReviewResult`：
  - `result.isFailed()` → 抛 `BizException(5705, "Rust 审核失败: " + error)`，
    由 `runEngine` 统一 `failTask`（保留真实原因）。
  - 审核已启动（`startReview` 成功）后轮询到 404 → 视为引擎丢失状态，
    抛 `BizException(5705, "Rust 审核状态丢失（引擎可能重启），请重新发起审核")`。
  - 保留 30 分钟总超时作为最后兜底。
- `recover()` 保持现状（磁盘兜底可恢复时仍可恢复）。

### F3（Java）孤儿任务守护
- 新增 `RunningTaskRegistry`（Spring 组件）：并发安全的 running-key 注册表，
  替代 `AuditEngineServiceImpl` 内 `private static RUNNING_TASKS`。
- 新增 `OrphanAuditTaskSweeper`：
  - `@Scheduled(fixedDelay = audit.orphan.sweep-interval-ms, 默认 60000)`
  - 查询 `task_status=PROCESSING 且 updated_at 早于 now-staleAfter` 的任务
  - 跳过仍在 `RunningTaskRegistry` 的任务（线程存活）
  - 其余：先 `recover()`；recover 失败 → `markFailed(清晰孤儿文案)` + 发 SSE COMPLETE
  - 全程 `TenantContext.wrap` 保证租户隔离
  - 开关：`audit.orphan.enabled`（默认 true）
- 效果：任何原因（Java 重启 / Rust 重启 / 线程死亡）产生的孤儿，
  最长 staleAfter+interval 后被判失败并通知前端，不再永久滞留。

### F4（Java）Rust SSE 断线重连
- `RustSseClient` 新增 `connectWithReconnect(docId, onEvent, shouldStop, policy)`：
  - 连接或流中断 → 指数退避重连（默认 1s,2s,4s,8s,16s，最多 5 次）
  - `shouldStop` 为 `Supplier<Boolean>`：done/error 已收到或任务已结束则停止
- 抽 `SseRetryPolicy`（纯逻辑，可单测）。
- 审核流程改用重连版；Chat 流保持原一次性连接。

### F5（Java）startReview 超时语义修正
- `RustApiProperties` 新增 `reviewStartTimeoutMs`（默认 30000）。
- `startReview` 请求超时改用该值；连接超时仍为 `connectTimeoutMs`。

### F6（运维）发布护栏
- 新增 `deploy/lib/audit-guard.sh`：
  - `has_active_audit_tasks()`：`docker exec aib-mysql mysql ...` 查询
    `SELECT COUNT(*) FROM audit_task WHERE task_status IN (0,1)`
  - 兼容 `AIBID_MYSQL_*` 环境变量覆盖，便于测试
- `update.sh` / `rollback.sh`：重建前调用护栏；存在在途审核时默认中止，
  打印提示，`--force` 可跳过（回滚场景需要）。

## TDD 测试策略

### Rust（`cargo test --lib`）
1. `review_state` 模块单测（tempdir）：
   write→read 往返、failed 覆盖、remove、损坏 JSON 容忍
2. `disk_recovery` 纯函数单测：
   状态文件 running→interrupted failed；failed→原错误；无文件→None；result.json 优先
3. `get_review_result` 集成单测（沿用 tests mod 风格）：
   模拟重启后（内存空 + 状态文件 running）返回 failed+中断文案
4. 既有 `review_result_preserves_partial_failed_status` 等全部保持绿色

### Java（`mvn test`，JUnit5 + Mockito）
1. `RunningTaskRegistryTest`：注册/移除/contains 并发语义
2. `OrphanAuditTaskSweeperTest`：
   - 陈旧 PROCESSING + recover true → 不标失败
   - 陈旧 PROCESSING + recover false → markFailed(孤儿文案) + SSE COMPLETE
   - 新鲜任务 / 非 PROCESSING / 注册表存活任务 → 不动
   - 租户上下文传播正确
3. `AuditEngineServiceImplTest`（新增）：
   - result=failed → failTask 携带 Rust error
   - 审核已启动后 404 → failTask 状态丢失文案
   - 404 但审核未启动 → 继续等待（不误杀）
4. `RustSseClientReconnectTest`（JDK HttpServer 集成）：
   - 首连接发 1 事件后断开 → 重连 → 收到第二连接事件
   - done 后不再重连；达到上限停止；shouldStop 生效
5. `SseRetryPolicyTest`：退避序列、上限、shouldStop
6. `RustApiClientStartReviewTimeoutTest`（HttpServer 延迟响应）：
   10s 延迟 + 30s 超时成功（旧 5s 语义会失败）
7. 既有 24 个测试类全部保持绿色

### Shell
- `deploy/tests/audit-guard-test.sh`：stub `docker`/`mysql` 命令验证
  `has_active_audit_tasks` 在有/无在途任务时返回正确，`--force` 语义正确。

## 端到端验收标准（缺一不可）

1. 复现原始故障：发起真实审核 → 审核中重启 `aib-backend-rust` → **2 分钟内**任务转 FAILED，
   错误信息包含"中断/重启"，前端状态自动刷新（SSE COMPLETE）。
2. 正常审核端到端成功，findings 落库、SSE COMPLETE、progress=100。
3. 孤儿守护：手工制造陈旧 PROCESSING 行 → 一个 sweep 周期内被标记 FAILED 并推送事件。
4. 全量回归：`cargo test --lib` 与 `mvn test` 全部绿色。
5. 发布护栏：存在在途任务时 `update.sh` 中止；`--force` 可跳过。

## 执行顺序
1. Rust F1（含 D1 验收）→ 2. Java F2 → 3. Java F3 → 4. Java F4 → 5. Java F5 → 6. F6 → 7. 端到端验收
