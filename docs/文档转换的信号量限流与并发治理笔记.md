# 文档转换（LibreOffice）的信号量限流与并发治理笔记

> 记录日期：2026-08-27
> 范围：DOCX/DOC → PDF 预览与抽取
> 关联提交：`8ed13b3`（本地 soffice 转换）、`ecaf805`（非 root 加固）、`fccdedb`（Rust 侧对齐）

## 1. 要解决的三个问题

把上传的 `.doc / .docx` 转成 PDF 时，LibreOffice 是一个「重」外部进程：

1. **内存贵**：一次转换峰值可达数百 MB；并发一多直接内存爆炸（宿主机 7.7G 无 swap，尤其危险）。
2. **有共享态**：soffice 默认 profile 会并发互锁（"another instance running" / profile 锁）。
3. **可能卡死/泄漏**：进程 wait 不设限会挂住请求线程。

## 2. 治理方案：信号量限流打底，四层 + 一个非 root 底座

| 层 | 机制 | 取值 | 解决的问题 |
|---|---|---|---|
| ① 并发上限（核心） | `Semaphore(2)` + `tryAcquire(30s)` | `MAX_CONCURRENT_CONVERSIONS=2`，等 30s 拿不到就快速失败「文档转换服务繁忙，请稍后重试」 | 内存失控、雪崩 |
| ② 每调用隔离 | 每次转换独立 `-env:UserInstallation=file://<tmp>/profile` + 独立临时输出目录 | 每个调用一份 uuid 临时目录，用完删除 | profile 互锁 |
| ③ 超时强杀 | `waitFor(60s)` → `destroyForcibly()` + 杀整棵进程树（含孙进程） | `CONVERT_TIMEOUT_SECONDS=60` | 卡死、进程泄漏 |
| ④ 结果缓存 | `.preview-cache`，key = `SHA-256(绝对路径 + "|" + mtime)` 取前 24 hex | 命中直接返回 PDF，不进转换 | 稳态转换量 ≈ 0 |

安全底座（非限流本身，但同属治理）：`runuser -u soffice -- soffice ...`，JVM/axum 仍以 root 跑、只有 soffice 子进程降到专用系统用户 `soffice`（uid 999），降低处理不可信文档的权限。

## 3. 关键取值依据

- **信号量 = 2**：单次转换内存峰值高 + 宿主机内存紧，2 是「吞吐 vs 内存」的平衡点；配合缓存，真正并发 ≥ 2 的场景很少。
- **等待 30s**：短请求容得下排队、又不让用户等太久；超时给明确错误而不是无脑阻塞。
- **超时 60s**：正常单文件（含 NotoCJK 渲染）远小于 60s，超过即判定异常。
- **隔离 profile**：runuser 后目标用户 HOME=`/home/soffice`，若不隔离 profile，并发仍会撞 `/home/soffice/.config/libreoffice/4` 锁。

## 4. 为什么「每次拉起进程 + 限流 + 缓存」够用，不上常驻实例/池化

- 转换**不是常态路径**：有缓存后稳态命中率高，真的需要转换的次数很少。
- 每次进程 = 无生命周期管理、无常驻进程僵尸化、无 first-run 重初始化。
- 唯一代价是冷启动 1~3s，这应靠「异步化 + 缓存」消解，而不是靠「常驻」。
- 常驻 office 进程自身有崩溃/僵死/状态污染风险，治理成本反而不低。

## 5. Java / Rust 对齐情况

| 端 | 非 root | 独立 profile | 独立临时目录 | 信号量限流 | 缓存 |
|---|---|---|---|---|---|
| Java `DocumentPreviewService` | ✅ runuser | ✅ | ✅ | ✅ Semaphore(2) | ✅ .preview-cache |
| Rust `docx_convert_service` | ✅ runuser | ✅ | ✅ | ❌（暂未显式限流） | ❌（暂未做） |

Rust 侧调用点分散（审核/知识库抽取）、并发天然低，暂未加信号量；若未来抽取接口被高频调用，在 services 层套同样的 `Semaphore` 即可。

## 6. 何时需要升级（触发清单）

出现以下信号再动，**逐一命中**才值得上池化：

1. 缓存命中率明显下降 / 大量不同文件同时首次预览；
2. 「文档转换服务繁忙」频繁出现（信号量被打满）；
3. 冷启动 1~3s 成为体验瓶颈。

手段优先级（从轻到重）：

`调大信号量（内存允许）` → `转换异步化（HTTP 不阻塞）` → `带 max-idle 的短生命周期进程池（最后才考虑）`

## 7. 与 `a9476be` 内存上限的关系（重点观察项）

`a9476be` 给 backend-java 加了 `mem_limit: 1536m` + `JAVA_TOOL_OPTIONS=-Xmx1024m`：

- JVM 堆上限 1G + 2 个并发 soffice（每个峰值数百 MB）在 1.5G cgroup 里**理论上**有 OOM-kill 风险。
- **实际风险低**：缓存让冷转换稀疏、信号量 2 已是上限。
- 若真观察到 java 容器被 OOM-kill：**优先**把 `MAX_CONCURRENT_CONVERSIONS` 降到 1，或把 `mem_limit` 提到 2g；**不要**先拆信号量。
