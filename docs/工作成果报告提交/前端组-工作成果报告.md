## 3. 解决方案与实现

### 3.1 方案说明

- **高亮为什么走 overlay 而非 DOM 属性写入**：基线往 react-pdf 的 textLayer DOM 写 `data-pdf-hit` 属性，在 React 19 + react-pdf v10 下触发 `insertBefore` 崩溃。改为纯 overlay 矩形渲染，零 DOM 写入，同时根治了崩溃。
- **bbox 为什么走 `chunk_map` 旁路而不改 `Chunk` 结构**：在 Rust `coordinator.rs` 新增 `chunk_map` 通道（`with_chunk_map`），从 `chunk.bbox_refs` 聚合 `block_ids`，避免改动可能影响合并的 Rust 主链路函数。这一取舍也源于我们与后端主链路协同不够紧密，选择了更保守的旁路方案。
- **SSE 为什么用 `fetch + ReadableStream` 而非 `EventSource`**：`EventSource` 无法携带 `Authorization` 与 `Last-Event-ID` 头，而重连续传必须带这两个头。

### 3.2 关键实现

**任务 1 — bbox 高亮链路（commit `601d58e`，cici）**
- Rust 侧：`coordinator.rs` 新增 `chunk_map` 通道；流式发射 `FindingAdded` 时从 `chunk_map` 聚合所有 `clause_ids` 对应的 `block_ids`；修复两根因：① 原只取 `clause_ids.first()` 单 chunk（漏聚合）；② 移除 `.take(5)` 截断；并过滤 lopdf 降级产生的占位假框。
- 前端侧：`PdfPreview.tsx` 改为纯 overlay `highlightBboxes`，基线 2 处 DOM 属性写入（`removeAttribute` / `setAttribute`）→ 现状 0 处。


**任务 2 — SSE 流式（commit `43efcec`、`2a88e4c`，cici）**
- 重连：指数退避 `SSE_BASE_DELAY_MS=1000`、`SSE_MAX_RETRIES=5`、`Math.min(1000 * 2^(retries-1), 30000)` 硬上限；重连带 `Last-Event-ID`（从 localStorage `auditLastEvent:{taskId}` 读）。基线 0 重试 → 现状 226 行含完整重试循环（重试关键字匹配 7 处）。
- 去重：`useAuditTask.ts` 的 `upsertIssues(prev, mapped)` 按 `riskId` upsert，应对 Java 双发 `finding_added` + `issue`。
- Token 并发：`request.ts` 的 `refreshPromise` 单例（基线 0 次 → 现状 6 次），多 401 共享同一刷新，避免互相覆盖踢下线。

**任务 3 — 租户管理页（commit `b9e1b2d`、`e19791a`、`2a88e4c`，cici）**
- 从零新建 `features/tenant/`：7 个文件、757 行，基线 0 文件。
- `tenant.ts` 的 6 个方法（`getTenants` / `createTenant` / `getCurrentTenant` / `getMembers` / `switchTenant` / `refresh`）与 Java 侧契约**一一对齐、无遗漏**。
- 其余成员管理类操作（邀请 / 移除 / 改角色）本期未实现——这部分源于**前后端接口契约对齐仍不充分**。

## 6. 结果分析

- **工作目标是否完成**：三项任务机制层面均已完成；量化验证仅部分覆盖。
- **结果能否证明改动有效**：编译全绿、单测全绿、重试上限可控，证明前端侧稳定性达标；高亮与流式「质量」层面尚缺量化证据，不能断言「准确率 / 完整率达标」。
- **符合 / 不符合预期**：代码机制符合预期；数据完整性低于预期，原因在于我们未补实验、验证工作没做到位，这是我们应直接承担的责任。
- **主要原因**：本期聚焦「让功能在代码层面跑通」，但端到端联调、量化验证与人工验收都被推迟；更深层的原因是**我们没有及早把可运行环境搭好、没有主动与后端完成联调**，导致验证只能停留在前端自洽层面。
- **偶然性 / 适用范围**：单测全绿依赖 luomo233 PR#21 提供的用例。

## 8. 反思与不足
1. **与后端对接不够主动、不够充分**。我们更多停留在前端代码自洽的层面，没有尽早和后端同学把接口契约、运行流程对齐清楚，导致部分能力（如成员管理写操作、SSE 租户隔离）停留在「契约未确认」状态，没能一气呵成闭环。这是协作上的失职。
2. **本地运行环境没有配置好**。我们明知项目需要 Docker + Rust + Java + 前端四层联动，却迟迟没有把一套可跑通的环境搭起来，以至于只能在类型检查、单测层面自证，无法做端到端联调，也无法为汇报提供真实演示。环境问题是客观存在的，但把环境准备好本就是我们该做的事，不应等到最后才暴露。
3. **验证工作做得不扎实**。量化实验（高亮准确率、SSE 完整率、重连成功率等）与页面人工验收都推迟了，使得「功能可用」缺乏硬证据支撑。验证滞后是我们自身的问题，不是外部原因。
4. **进度管理被动**。以上三点叠加，客观上拖慢了项目整体进度。我们应在开发早期就并行推进环境搭建与前后端联调，而不是把验证压到最后。

**改进方向**：后续每实现一个功能，就同步推进（a）与后端确认契约、（b）在可运行环境里联调、（c）补量化实验与截图验收，把「能跑、能演示、有数据」作为完成的硬标准，不再把「代码写完了」等同于「工作做完了」。
