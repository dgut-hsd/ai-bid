# 知识沉淀引擎反馈



---

## 1. 评审结果

当前知识沉淀产出的是一个**实体索引骨架**（`风险类型 → 法条 → 条款号`）。行业里真正被复用的是一个**完整案例**（`事实 + 判定 + 依据 + 理由 + 处置`）。本方案把沉淀单元从"法条图谱"升级为"案例五要素"，并把复用路径打通。

## 3. 升级依据：该复用的是什么

### 3.1 行业先例库复用"理由 + 决定"

政府采购领域最权威的经验沉淀物——财政部《指导性案例》与各级财政厅《投诉处理决定书》——固定结构为：**案情简介 + 争议焦点 + 法律依据 + 处理理由 + 处理决定**。
被反复援引、真正产生复用价值的，是"处理理由"和"处理决定"两栏，而非"案例编号 + 法条号"。

来源：[财政部政府采购指导性案例10号](https://czj.ganzhou.gov.cn/gzsczj/c103007/202512/485a3333f2c8462cad501eac51a73eb0.shtml)、[辽宁省财政厅典型案例通报](http://ggzy.ln.gov.cn/ywdt_1/hydt/zcwj/zfcg_149551/sjzc/202606/t20260626_5644104.html)、[陕西省行政裁决典型案例](http://gxt.shaanxi.gov.cn/webfile/zbjg/87373.html)

### 3.2 法律 AI 的"案例检索"召回带推理的案例

法律 RAG 的核心是 *case retrieval + reasoning*：召回相似案例后，把**该案例的完整理由**喂给模型做增强生成。类比的载体是"事实 + 理由 + 结论"，不是法条编号。

来源：[CLERC: Legal Case Retrieval and Retrieval-Augmented Analysis Generation](https://aclanthology.org/2025.findings-naacl.441/)、[Mitigating Legal Hallucinations via Symbolic Constraints and Analogical Precedents](https://aclanthology.org/2026.acl-long.633/)

### 3.3 Agent 记忆："经验是资产"的前提是"检索时上下文可用"

记忆的价值 = 可被检索 + 被检索时能给出可用上下文。只存 `risk_type` 标签，给到 Agent 的上下文厚度约等于零，等于没复用。

来源：[Memory Retrieval Strategies for AI Agents](https://mem0.ai/blog/memory-retrieval-strategies-for-ai-agents/)、[腾讯云：Agent 经验沉淀成资产](https://cloud.tencent.cn/developer/article/2720807?policyId=20240000&traceId=&frompage=homepage#1)

## 4. 升级目标：以"案例五要素"为沉淀单元

一条可复用的经验定义为：

```
案例 = {
  事实锚点 : source_quote        ← 召回键（语义/向量匹配"新条款像不像老案例"）
  判定标签 : risk_type + severity ← 结构化过滤 + 排序
  权威依据 : legal_basis          ← 溯源 + 结论可信度
  论证理由 : reason               ← 类比的关键（上次为什么这么判）
  处置方案 : suggestion           ← 最直接的一次复用产出（该怎么改）
}
```

对应到 `RiskFinding` 的字段映射：

| 案例五要素 | RiskFinding 字段 | 升级后落点 |
|-----------|-----------------|-----------|
| 事实锚点 | `source_quote` | Experience 节点 / 案例库 payload |
| 判定标签 | `risk_type` + `severity` | Risk 节点（保留） |
| 权威依据 | `legal_basis` | Law / Article 节点（保留） |
| **论证理由** | **`reason`** | **Experience 节点（新增）** |
| **处置方案** | **`suggestion`** | **Experience 节点（新增）** |

> 新增:`reason` 与 `suggestion` 不是"可要可不要的元数据"，而是**复用价值的本体**；`source_quote` 是"钥匙"（负责让案例被命中），不是"内容"。

## 6.预期效果


目前实现已经达到基本规格——`collect / extract / graph` 三段的逻辑正确、单元测试 30/30 绿。但目前证明不了经验被复用。真正要验收的是：**每次审完，这次的经验有没有完整进系统、下次能不能被搜到并被 Agent 直接用上。** 按这条口径，当前是未实现的，缺在三个地方：

1. **经验被阉割了**。`extract.rs:322` 把 `reason / suggestion / confidence / case_refs` 全丢了，只留下 `risk_type + 法条 + source_quote`，字段保留率 4/8。而"经验"的本体恰恰是被丢掉的那两个——`reason`（为什么判）和 `suggestion`（怎么改），行业里的先例库复用的就是"处理理由 + 处理决定"，缺了它们沉淀下来的只是一张目录，不是经验。
2. **历史经验会被冲掉**。`graph.rs:76-77` 的 `ON MATCH SET r.snippet = $snippet` 是覆盖式，同一风险类型多次出现只留最后一次。


所以判定口径是：**函数写对了，但场景目标"审完 → 经验反馈 → 下次搜到/复用"未实现**。阶段一补字段、改累加，能让字段保留率 4/8 → 8/8；阶段二让经验案例进库。最后验收：审 A 审到"地域歧视"，下次审同类条款时，Agent 能命中这条案例、并拿到上次的 `reason` 和 `suggestion`。

评审红线三条：不允许用"单元测试过"顶替"经验可复用"；不允许把 `source_quote` 当 `reason/suggestion` 的等价物；`search` 接口存在不等于 Agent 真的检索到了经验，需要调用单个Agent函数进行测试。
