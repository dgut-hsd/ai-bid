## 5. 问题所在（问题诊断）

### 5.1 现象

在一份规范、已备案的真实磋商文件上，引擎命中 32 条，复核后 0 条属实。命中的 32 条全部是被误判的正常条款，其中 62%（20 条）集中在 `SHORT_DEADLINE` 一类。

### 5.2 直接原因（规则层病灶）

属于“某几条规则写得太宽”的表层问题，可从规则文件直接定位：

- `TIME_SHORT_DEADLINE`（`conditions.yaml`）使用 `check: any_match`，且 `patterns` 含关键词 `["不足","少于","仅有","只有","不满"]` 与正则 `'[1-9]\s*日.{0,6}(内|以内|之后|前)'`，任一模式单独命中即触发；
- `engine.rs` 硬编码中 UNRELATED_CERT 分支用 `["认证","证书","荣誉",…]` 与 `["资格","无效","废标","必须","须提供",…]` 共现判定；
- `SAFE_ACCEPTANCE_ABSENCE`（`conditions.yaml`）以 `match_mode: absence`“未提及『安全生产许可证』即命中”。

以上是“病灶”，但不是问题的根本。

### 5.3 根本原因（方法论层缺失）

这套引擎的根本问题在于：**它把“自然语言是否违规”这道语义判断题，交给了“字符串子串匹配”这种无语义的机械操作**。具体表现为三种缺失：

**缺失一 · 规则作用在“原始字符串”上，而非“语义要素”上**

规则匹配的对象是字符序列（`contains("少于")`），而不是语义判断（“投标准备期限 < 法定最短期限”）。结果是同形异义被混为一谈：“不得少于 10 个日历日”（表达 `≥`）与“少于 10 个日历日”（表达 `<`）字面都含“少于”，语义相反，却被归入同一规则。行业对照参见第 6 节指引 A：先做要素抽取，规则作用在结构化要素上。

**缺失二 · 否定与比较语义未建模**

“不得少于 / 不予接受 / 不因…顺延”这类否定结构没有被识别，因此“不得少于”被读成“少于”。这属于自然语言处理中的否定检测（negation detection）与语义极性判断，是当前实现完全缺失的能力。

**缺失三 · 无证据定位与上下文约束，导致“召回”被当成“判定”**

命中结果只返回类别码，不返回“由哪几个字、在什么上下文触发”。叠加 `any_match` 使单一关键词即可拍板“违规”，等于把“疑点召回”直接当成了“最终判定”。而规则命中在行业做法中只应是“召回 + 证据 span”，最终判定由精判环节承担（指引 B）。

### 5.4 问题的一句话定义

本引擎的核心问题不是“某条规则写错”，而是**架构上缺少“语义要素抽取 + 否定识别”这一层，并把无语义的字符串匹配直接当成了最终判定**。白盒测试无法暴露此问题（白盒是按规则出题），只有黑盒真实语料才能暴露。

## 7. 结论（事实陈述）

1. 规则引擎能够正确执行其声明的规则（白盒验证 `4 passed`）。
2. 规则引擎在独立真实语料（302 条）上，命中 32 条，逐条复核后 0 条构成实质性违规，Precision = 0%。
3. 表格层面原因是若干规则（`TIME_SHORT_DEADLINE` 的 `any_match`、硬编码关键词共现、`absence` 模式）过宽。
4. 根本原因是引擎以原始字符串为匹配对象、缺少语义要素抽取与否定识别，并将“召回”直接当作“判定”。
5. 该缺陷只能由独立真实语料的黑盒验证暴露，自测（白盒）不能暴露。

## 9. 规则引擎应达到的程度

### 9.1 职责边界

- 规则引擎**适用**的判断：确定性、可枚举、结构化后可逻辑表达的条件（例：“投标准备期天数 < 20”“保证金比例 > 2%”）。
- 规则引擎**不适用**的判断：依赖语境、价值权衡、开放式语义（例：“是否构成以不合理条件限制潜在供应商”），此类归精判环节。
- 规则命中的合理角色：**候选线索 + 证据定位**；最终判定不归属规则引擎。

### 9.2 能力程度分级

**L1 · 不可用（本次验证所处程度）**

| 项目 | 状态 |
|---|---|
| 匹配对象 | 原始字符串 |
| 否定 / 比较语义 | 无 |
| 证据定位 | 无（仅返回类别码） |
| 命中语义 | 命中即结论 |

表征：白盒可全绿，黑盒 Precision = 0%（见第 3 节）。

**L2 · 可用（合格线）**

| 项目 | 状态 |
|---|---|
| 匹配对象 | 结构化语义要素（先抽取要素，再对要素判规则） |
| 否定 / 比较语义 | 具备（“不得少于”识别为 ≥ 并排除） |
| 证据定位 | 命中附带触发原文片段 |
| 命中语义 | 候选线索，由精判环节决定 |

表征：规则命中的误报可控；Recall 由精判环节兜底。

**L3 · 可靠（进阶线）**

| 项目 | 状态 |
|---|---|
| 推理方式 | 自然语言条款转逻辑谓词后做确定性推理 |
| 评估体系 | 具备独立 golden 集，可回归 P / R / F1 |
| 可解释性 | 每条结论可回溯到“证据原文 → 规则 → 逻辑链” |

表征：准确率可量化、可复现、可审计。

### 9.3 判断“是否达到”的执行标准

以下四项可作为衡量“距离可用还有多远”的对照项，括号内为本次验证的现状：

1. 存在一份独立于规则编写过程的测试集，可在其上报告 Precision / Recall / F1（**当前：无，Recall 无法量化**）。
2. 每条命中可回溯到触发它的原文证据（**当前：仅返回类别码**）。
3. 否定结构（不得少于 / 不予接受 / 不因…顺延 等）不再产生语义反转误报（**当前：产生，见第 4.1 节**）。
4. 规则命中不再直接等同于最终判定，而是作为进入精判环节的候选线索（**当前：命中即结论**）。
