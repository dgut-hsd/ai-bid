# 审核结果一致性设计

> 状态：P1/P2 已落地并部署验证；P3 判定为与 P2 重复、不做单独通道；P4 核实既有机制已覆盖、仅做阈值加固。
> 相关代码：`backend-java`（AuditEngineServiceImpl / AuditTaskServiceImpl）、`frontend`（useAuditTask / IssueListPage）、`backend-rust`（review_state.rs）。
> DDL：`deploy/db-migrations/001-audit-consistency.sql`。

## 1. 问题现象

1. 前端列表页显示某标书「已审核完成」，但点进去结果为空。
2. 重新打开窗口，之前已审核的数据“消失”。
3. 审核进行中退出再进入，状态回退成「准备审核」。

这三个现象是同一组根因在不同入口的表现，不是数据被删，而是**“任务和结果的定位方式不可靠 + 结果只存在于易失层”**。

## 2. 根因（三处叠加）

### R1：任务指针只存在浏览器 localStorage
- 前端用 `localStorage['auditTask:'+bidId]` 记忆 bid → taskId；`startAudit` 写入，`hydrate` 读取。
- 关键缺陷：`hydrate` 的 `catch` 里 `localStorage.removeItem(storageKey)`——任何一次网络抖动/5xx/解析错误都会**永久抹掉指针**，下次进入就只能落到「准备审核」。
- 换设备/清缓存/多标签页时，指针天然缺失。

### R2：审核进行中的 finding 是“易失”的
- Rust 实时 finding 走 `emitTransient`（只推 SSE、不落 `audit_task_event`）。
- `audit_issue` 表只在 `completeTaskFromReview`（任务完成那一刻）全量重建。
- 结论：进行中退出，DB 里没有进行中的 finding；Rust 重启则连内存里的也没有。

### R3：`getResult` 对非 COMPLETED 直接返回空
- 未完成任务 → `{auditResult:"pending", issues:[]}`，不读 `audit_issue`。
- 即使有部分结果，也读不出来。

## 3. 设计原则

1. **服务端是任务裁决的唯一事实来源**：bid → taskId 由后端按「该 bid 的最新任务」裁决，前端 localStorage 只做“临时提示”，不作为裁决依据。
2. **`audit_issue` 是 finding 的持久增量存储**：审核进行中即持续落库，完成时对账；任何时刻 DB 都是可恢复的真相。
3. **恢复不依赖“重放顺序”**：读库拿结果 > 依赖 SSE 快照重放（避免多通道漂移）。
4. **失败不清数据**：前端错误路径禁止删除指针/结果；任务失败不清空已落库的 finding。

## 4. 分阶段实现

### P1 —— bid→taskId 服务端裁决 + 前端去 localStorage 依赖（✅ 已落地）

后端：
- `AuditTaskServiceImpl` 抽出统一的状态构建 `buildStatusVO`，新增
  `getStatusByBid(bidId)`（`findLatestTaskByBidId` 取该 bid 最新任务，无任务返回 `taskId=null/status=pending`）。
- `AuditTaskController` 新增 `GET /api/audit-tasks/by-bid/{bidId}`。

前端：
- `useAuditTask.hydrate` 与 `IssueListPage` 改为先调 `getStatusByBid(bidId)`；
  `taskId=null` → 显式「准备审核」；有值则回写 localStorage 缓存。
- **删除 catch/failed 分支里的 `localStorage.removeItem`**：只在明确“从未发起/资源不存在”时复位，网络/5xx 一律保留指针与 taskId，交 3s 轮询兜底重试。
- `AuditStatus.taskId` 类型改为 `string | null`。

### P2 —— findings 增量落库 + getResult 统一读库（✅ 已落地）

数据结构（`deploy/db-migrations/001-audit-consistency.sql`）：
- `audit_issue` 增加 `risk_id VARCHAR(64)`；唯一键 `uk_audit_issue_risk(tenant_id, audit_id, risk_id)`。
- 既有行回填 `risk_id = SUBSTRING(issue_no, 7)`（修复 DB 兜底重建时的 `ISSUE-ISSUE-` 双前缀）。

后端：
- `AuditIssueMapper.upsert`（`INSERT ... ON DUPLICATE KEY UPDATE`）按唯一键去重。
- `AuditEngineServiceImpl` 抽出统一映射 `toIssue(task, finding, seq)`；finding_added/updated → `persistFindingIncremental`，finding_removed → `deleteFindingIncremental`；`completeTaskFromReview` 复用 `toIssue` 并写 `risk_id`。
- `getResult` 移除「非 COMPLETED 提前返回空」：统一从 `audit_issue` 读（进行中的增量 + 完成后的最终）；`auditResult` 进行中=`pending`，完成=`pass/revise`。

前端：
- `useAuditTask.hydrate` 的“进行中”分支额外 `getAuditResult` 拉取已落库 finding 种子展示。

### P3 —— SSE findings 快照重放（⏭️ 不单独实现，理由见下）

原方案：把 finding 事件写成防抖 `findings_snapshot` 事件，让 SSE `Last-Event-ID` 重放能还原 finding。

**结论：P2 落地后此通道冗余**——`getResult` 已经能从 `audit_issue` 读回进行中的 finding，且前端已有两处触发：`hydrate` 种子拉取 + 每 3s 的 `syncStatus` 轮询（`hasResult` 时回填 issues）。因此无论“整页刷新”还是“瞬时 SSE 断线漏事件”，都能在 ≤3s 内从 DB 拉回，无需再维护一套快照重放通道（多通道还引入顺序/去重不一致风险）。故 P3 不做。

### P4 —— Rust 状态可查询 + 中继重连 + 孤儿阈值（✅ 核实已覆盖，做了阈值加固）

核实结论（既有机制已满足设计意图，无需新写 Rust 端点）：
- **Rust 状态落盘**：`backend-rust/src/api/review_state.rs` 已在 POST /review 被接受时写 `{doc_id}_review_state.json`（running），完成/失败改写；`GET /review/:doc_id/result` 的磁盘兜底据此区分 completed / running / failed / 404。Java `recover()` 据此返回 COMPLETED / STILL_RUNNING / FAILED / STATE_LOST / UNREACHABLE。
- **中继重连**：`RustSseClient.connectWithReconnect` 已是带退避的重连实现。
- **孤儿守护安全**：`OrphanAuditTaskSweeper` 对 PROCESSING 先 `recover()`，仅 `STATE_LOST/NOT_FOUND` 才失败，`STILL_RUNNING/UNREACHABLE` 留给下一轮——不会误杀仍在跑的审核。
- **失败保留部分结果**：`failTask` 不删 `audit_issue`，P2 的增量行保留。

本次加固：
- `application.yml` `audit.orphan.stale-after-ms` 由 180000 上调到 600000（10 分钟），对齐单份标书 Multi-Agent 审核的实际时长，减少 JVM 重启后对仍在跑的审核的无效 recover 抖动。
